# Fluffy Packaging & System Architecture Notes

## Core Design Principles

1. **Per-Package Squashfs Images (`/sw/<pkg>`)**
   - Every package builds and installs into `/sw/<pkg>` (e.g. `/sw/man-pages`, `/sw/zlib`), which is packaged as `sw/<name>-<version>.squashfs` with `-all-root -comp zstd`.
   - At runtime and build time, the squashfs image is mounted at its unversioned mountpoint `/sw/<pkg>`.
   - Upgrading a package means mounting a newer `.squashfs` at `/sw/<pkg>` in the new mount namespace—no RPATH or path rewriting needed.
   - **Why SquashFS? (The Architectural & Security Rationale)**:
     - **Installation Almost *Isn't***: There is no file extraction, tar unpacking, or payload copying. Installing a package is literally a single kernel `mount` syscall ($O(1)$ time complexity).
     - **Inherently Read-Only by Design**: The underlying filesystem format is immutable. Even the `root` user cannot accidentally clobber, mutate, trojan, or delete files inside `/sw/*`.
     - **Cryptographically Verifiable Forever, Even After Installation**: Because the package is mounted directly from its signed `.squashfs` image rather than extracted into loose files, verifying the package's integrity across its entire lifecycle on the machine is as trivial as checking the image's hash in `/sw/.build/fstab` (and, once published sets are downloaded, the signature blessing that set). There is zero file-level bit rot or stealth file tampering.
     - **Clear Security Boundary**: Only `root` can mount anything into `/sw/`. The system attack surface is exceptionally easy to reason about and audit.
     - **Self-Documenting File Ownership**: The pathname `/sw/<pkg>/...` directly and unambiguously identifies which package owns every binary, library, header, and asset on the system with zero database queries (`dpkg -S`, `rpm -qf`).
     - **Transparent Deduplication & Compression**: Zstandard compression at rest with shared page cache entries across all processes, containers, and namespaces on the host.

2. **Immutable Mount Namespaces via PID 1 `setns` Cutover (Zero Torn Installs, Zero Per-App `unshare` Overhead)**
   - Running processes inherit PID 1's mount namespace normally at launch—no per-shell or per-app `unshare(CLONE_NEWNS)` wrapper is needed!
   - When packages are upgraded or removed, `swctl` constructs a brand-new mount namespace (`CLONE_NEWNS` with `MS_PRIVATE`), mounts the complete target `/sw/*` closure inside it, and hands that namespace FD to PID 1 (`systemd`) across `systemctl daemon-reexec` (`setns(fd, CLONE_NEWNS)` in `finish_reexecute()` immediately prior to `execv()`).
   - Because PID 1 moves into the *new* mount namespace rather than mutating the old namespace in place, **every pre-existing process stays undisturbed inside the untouched prior mount namespace**—never experiencing a torn upgrade (e.g. halfway through loading shared libraries or reading data files while files change underneath).
   - **Desktop / Interactive UX**: Any newly spawned systemd service, new login session, or terminal/launcher that enters `/proc/1/ns/mnt` immediately lands in the upgraded generation, while already-running apps continue uninterrupted in the previous generation's namespace until restarted.
   - Old `.squashfs` mounts stay alive in previous generation namespaces until the last process using them exits.
   - **New Installs vs. Package Upgrades**:
     - **Fresh Package Installs (Additions)**: Do *not* even require a new mount namespace. Mounting a brand-new package at `/sw/<pkg>` in `/proc/1/ns/mnt` carries zero risk of torn state since no active process was running against it, making newly installed commands available immediately in existing shells.
     - **Package Upgrades / Removals**: `swctl` stages a fresh generation mount namespace and transitions PID 1 into it via `daemon-reexec`, leaving existing processes pinned safely to the prior untouched namespace.

3. **Stateless `/etc`: Read-Only Package Defaults (`/sw/*/etc/<file>`) & `/etc/<file>` User Overlay**
   - **Package Creation vs. System Configuration**:
     - Package creation (`swctl build`) builds hermetically and **never** touches `/etc`. All package-supplied default configuration files install strictly into `/sw/<pkg>/etc/` inside the read-only `.squashfs` image (zero copy, zero mutable package state).
     - `/etc` belongs strictly to the user/administrator. Mounting, upgrading, or removing a package in `/sw/<pkg>` never mutates `/etc` or runs background mount/post-install hooks (`fluffy-upsert` / `fluffy-init` are eliminated). When user-level setup is desired, users explicitly edit `/etc` or invoke commands that write directly to `/etc`.
   - **No `.d/` Drop-In Directories Needed (`/sw/*` *Is* Already the Drop-In Namespace)**:
     - Traditional FHS distributions invented `foo.d/10-bar.conf` drop-in directories only because dozens of packages were forced to share a single flat `/etc` directory without filename collisions or fragile post-install `sed` edits.
     - In Fluffy, `/sw/*` already isolates every package into its own directory: packages ship plain `/sw/<pkg>/etc/<file>` (e.g. `/sw/iana-etc/etc/services`, `/sw/iana-etc/etc/protocols`, `/sw/systemd/etc/passwd`, `/sw/dbus/etc/passwd`, `/sw/bash/etc/profile`) with zero collisions and zero `10-`/`50-` numbering bikeshedding, while `/etc/<file>` has a single owner—the local administrator—who writes only the lines they actually customize (e.g. a 2-line `/etc/hosts` or a 1-line override in `/etc/passwd`).
     - **Target Minimal Boot State**: A freshly bootstrapped Fluffy system requires almost nothing on mutable root beyond `/etc/fstab`, `/etc/fluffy/fstab`, `/etc/machine-id`, `/etc/shadow` (for `root`'s local password), basic `/etc/systemd/network/` setup, `/init`, and `/boot/grub/grub.cfg`—every default user/group (`passwd`, `group`), `hosts`, `protocols`, `services`, `nsswitch.conf`, `os-release`, fallback `hostname`, `resolv.conf` stub fallback, shell profile, and default systemd unit/enablement comes straight out of `/sw/*`, with `/etc` strictly holding local overrides.
   - **Unified Multi-File Vendor-First, User-Last Semantics Across All `/etc` Consumers**:
     - Every configuration consumer is taught to consult multi-file vendor defaults across `/sw/*/etc/<file>` (and `/sw/*/lib/...` where applicable) with `/etc/<file>` always getting the final word:
       1. **Stateful / Accumulating ("Last Wins") Configs** (`profile`, `bashrc`, `fstab`, `sysctl.conf`, `login.defs`, etc.): Expand `"/sw/*/etc/<file>:/etc/<file>"` via `GLOB_PATHS` — evaluate vendor files from `/sw/*/etc/<file>` first, then apply `/etc/<file>` last so user settings override vendor defaults.
       2. **Record-Lookup Tables (`glibc` `nss_files` & `nsswitch.conf`) & Copy-on-Write `shadow` Mutations**:
          - Across `passwd`, `group`, `hosts`, `services`, `protocols`, `networks`, `ethers`, and `rpc` (plus `nsswitch.conf`), merge vendor records from `/sw/*/etc/<file>` with user overrides in `/etc/<file>` taking precedence (probing `"/etc/<file>:/sw/*/etc/<file>"` for $O(1)$-memory first-match lookups and deduplicating seen keys during `*ent()` / `initgroups` enumeration).
          - **Zero Vendor `shadow` Files**: Packages never ship `/sw/<pkg>/etc/shadow` or vendored password hashes. Daemon/service users in `/sw/<pkg>/etc/passwd` use `*` in `pw_passwd` with `nologin`/`false` (unshadowed locked accounts), while `root` (`pw_passwd = "x"`) gets its password set locally in `0600` `/etc/shadow` by `bootstrap.sh` (if unset).
          - **Copy-on-Write User/Group Tools (`sw/shadow`)**: Mutating tools (`passwd`, `usermod`, `chsh`, `gpasswd`) create `/etc/{passwd,group,shadow}` on demand if absent and materialize only the single modified NSS record into `/etc/<db>`.
       3. **Collision-Free Package UIDs/GIDs via `mkuid.sh` (`[1073741824, 2147483647]`)**:
          - Aside from kernel/ABI-fixed IDs (`root = 0`, `tty = 5` compiled into `systemd`'s `devpts` mount, and `nobody`/`nogroup = 65534` matching `overflowuid`), package-owned daemon users and groups allocate random static IDs in `[1073741824, 2147483647]` ($2^{30} \dots 2^{31}-1$) via `./mkuid.sh` at recipe authoring time, and `systemd`'s `uid_is_system()` / `gid_is_system()` recognizes `0x40000000..0x7FFFFFFF` as system accounts (routing logs to `system.journal` and avoiding human session creation while keeping `1000..60000` clean for `useradd`).
          - **Carve-outs systemd needs inside that range (2026-11-17).**
            - The container UID ranges are capped with `-Dcontainer-uid-base-max=$(( 0x3FFF0000 ))` in `sw/systemd`, so the last 64K container range ends at `0x3FFFFFFF`, below 2^30. Upstream's default runs up to `0x6FFFFFFF`. The value is written as bash arithmetic because Meson rejects hex in `-D` values.
            - systemd's foreign UID range `0x7FFE0000..0x7FFEFFFF` (`foreign-uid-base`, left at the upstream default) sits inside the package range. `mkuid.sh` never allocates there, and `--check` rejects any ID in it.
            - When this was added, all 49 allocated IDs were checked and none fell in that range, so nothing was reassigned. If `foreign-uid-base` ever changes, update `FOREIGN_MIN`/`FOREIGN_MAX` in `mkuid.sh` and re-run `./mkuid.sh --check` against every existing allocation.
       4. **System Identity & Resolver Fallbacks (`os-release`, `hostname`, `resolv.conf`)**: `systemd` reads `/sw/*/etc/os-release` (or `/sw/*/lib/os-release`) when `/etc/os-release` is absent and uses `-Dfallback-hostname=fluffy` when `/etc/hostname` is absent; `glibc`'s resolver falls back to `/sw/*/etc/resolv.conf` (e.g. `systemd`'s symlink to `/run/systemd/resolve/stub-resolv.conf`) when `/etc/resolv.conf` is absent.
   - **Systemd Unit & Enablement Ownership (Package Owns Feature -> Package Owns Unit; `/etc` Has Final Word)**:
     - Running `systemctl preset-all` into `/etc` (or leaving upstream `systemd`'s implicit `enable *` first-boot preset active) violates `/etc` ownership by dumping unowned symlinks into `/etc/systemd/system/*.wants/`, leaving dangling symlinks when packages are unmounted and failing to activate newly mounted packages (or clobbering user choices if re-run).
     - **Split Units & Default Enablements Into the Packages That Actually Own Them**:
       - `sw/util-linux`: Because `util-linux` is required for `agetty`, `util-linux` owns `getty` (`getty@.service`, `serial-getty@.service`, `console-getty.service`, `container-getty@.service`, `autovt@.service`, and `getty.target.wants/getty@tty1.service`), alongside `uuidd.{service,socket}` and `fstrim.{service,timer}` in `/sw/util-linux/lib/systemd/system/`.
       - `sw/systemd`: Owns core target/system units, `systemd-networkd` (plus default DHCP `.network` in `/sw/systemd/lib/systemd/network/`), `systemd-resolved`, `systemd-timesyncd`, `systemd-oomd`, and their `.wants/` and `dbus-*` symlinks in `/sw/systemd/lib/systemd/system/`, plus `disable *` in `99-default.preset` so PID 1 never pukes symlinks into `/etc`.
       - `sw/e2fsprogs` & `sw/man-db`: Own `e2scrub_all.timer` / `e2scrub_reap.service` and `man-db.timer` (plus their `timers.target.wants/` / `multi-user.target.wants/` symlinks) inside `/sw/<pkg>/lib/systemd/system/`.
     - **Vendor Consulted First, `/etc/systemd/system` Gets the Final Word**:
       - `systemd` loads vendor units, `.wants/`/`.requires/`, and drop-ins across `/sw/*/lib/systemd/system` (and `/sw/*/etc/systemd/system`), while `/etc/systemd/system` always has highest override precedence (final word on whole-unit replacement, `.d/*.conf` drop-ins applied last, `systemctl enable` for opt-in daemons like `sshd` with zero package install/uninstall hooks, and `systemctl mask` -> `/dev/null` for suppressing vendor-enabled units).
   - **Btrfs Snapshot Protection for `/etc`**:
     - The root filesystem uses **btrfs**, and `/etc` can be snapshotted across administrative changes for instant atomic rollback.

4. **Late-Bound `/sw/*/foo` Discovery (No Symlink Farms, Zero Hardcoded Package Ownership)**
   - **Principle of Late Binding**: Tools and libraries should never assume or hardcode which `/sw/<pkg>` provides a given header, library, executable, or data file. Instead, resolution should happen as late as possible by walking `/sw/*` alphabetically (`alphasort`) in the current mount namespace.
     - Even if a build tool (`configure`, a linker, etc.) resolves a `/sw/<pkg>/...` path during build, the input to that build should never require hardcoding `--with-foo=/sw/bar`. And wherever possible, runtime tools should traverse `/sw/*` dynamically (caching per-process, which is always safe because `/sw` mounts never change within a launched process's mount namespace).
     - **Why this matters**: Packages can be split into subpackages, merged, or reorganized later (e.g. `libstdcpp` separate from `gcc` vs. bundled) and everything continues to work with zero flag changes.
   - Concrete `/sw/*` discovery points:
     - **`PATH` (`/sw/*/bin` only — zero `sbin`)**:
       - Fluffy does not use `sbin` directories anywhere. All utilities, system binaries, and administrative daemons reside in `/sw/<pkg>/bin` (configured via `--sbindir=/sw/<pkg>/bin` or `rootsbindir=/sw/<pkg>/bin`).
       - `bash`: `findcmd.c` and `bashline.c` dynamically glob and iterate `/sw/*/bin` for command resolution and TAB completion.
       - `glibc`: `posix/execvpe.c` (`__execvpe_common`) parses wildcard PATH entries like `/sw/*/bin`, discovers all `/sw/<pkg>/bin` directories via `__getdents64` without heap allocations (`vfork`/`CLONE_VM` safe), and tests executables in alphabetical order. All POSIX execution APIs (`execvp`, `execvpe`, `execlp`, `posix_spawnp`) work transparently with literal wildcard `PATH`.
          - **Future Enhancement — `PATH`-Resolving `#!` via `binfmt_misc`** (decided strict, 2026-11-20; one deliberate exception to [GLOB.md](GLOB.md) Rule 3, below):
            - **Kernel-Level `#!` Resolution via `binfmt_misc` (`#!bash`, `#!perl`)**:
              - In the Linux kernel (`fs/exec.c`), `binfmt_misc` (`register_binfmt`, added at the head of `formats`) runs *before* `binfmt_script` (`insert_binfmt`, added at the tail) and applies to all `execve(2)` callers—including statically linked non-libc binaries like Go.
              - Since Linux 6.7+, `binfmt_misc` is per-user-namespace, so `swctl` (or a booted Fluffy system) can mount an isolated `binfmt_misc` instance and register a handler at `/sw/shebang/bin/shebang` on magic `#!` (with `P` `preserve-argv[0]` and `O` `open-binary` flags, and *without* `F` so the kernel resolves `/sw/shebang/bin/shebang` dynamically inside the caller's active mount/chroot namespace).
              - Because `binfmt_misc` invokes the handler in the calling process's context with its exact `envp` (including `PATH`), shebangs can honor the caller's `PATH` via `execvp()`—enabling pathless shebangs like `#!bash`, `#!sh`, `#!perl -w` or `#!python3`.
              - **Strict rules (decided 2026-11-20).** The handler owns every `#!` line; it never falls through to the kernel's `binfmt_script`, so this one program defines what a shebang means on Fluffy:
                1. *A bare name* (`#!bash`, `#!perl -w`): `execvpe(name, …)`, whose glob-aware `PATH` search (above) finds it in `/sw/*/bin`, in the same order as everything else. This is the idiomatic form.
                2. *A path* (contains `/`): `glob(path, GLOB_PATHS)` and `execve` the first match in byte order. So `#!/sw/*/bin/bash` works (accepted, not idiomatic): the one place a single executable path is a glob, an exception to GLOB.md Rule 3 made on purpose. A literal path matches only itself, so `#!/sw/bash/bin/bash` keeps working and today's rewritten scripts need nothing on day one; `#!/bin/sh`, `#!/usr/bin/env perl` and other FHS paths fail with ENOENT, as they do now. No compatibility mapping of `/bin/X` or `/usr/bin/env X` to a `PATH` lookup: that would be a symlink farm in code, and its temptation grows like one.
                3. *A relative path* (`#!./tool`): relative to the current directory, as the kernel treats it.
                - Kernel compatibility: everything after the interpreter is one argument, unsplit (`#!perl -w -T` gives `-w -T`); the interpreter gets `[interp, optional-arg, script, args…]`; a missing interpreter exits 127 naming the shebang and the script, as "bad interpreter" does; recursion (an interpreter that is itself a script) is bounded by the kernel's `BINPRM_MAX_RECURSION`; setuid scripts stay ignored, as Linux ignores them.
                - Files with no `#!` that fail with ENOEXEC are already covered: glibc's `execvp` falls back to `_PATH_BSHELL`, which Fluffy sets to `/sw/bash/bin/sh` (below).
                - Migration: the `#!/sw/bash/bin/bash` and `#!/sw/perl/bin/perl` rewrites in Fluffy's forks (zstd, git, curl, autoconf, libtool, gnulib, ...) keep working; each moves to the idiomatic `#!bash` / `#!perl` later, package by package, so shebangs follow `PATH` instead of naming Fluffy's layout.
              - **In tree, static, like `init` (2026-11-20).** The handler is a small C program kept in the repo as `sw/shebang.c` and built by `sw/shebang` the way `sw/init` builds `sw/init.c` (`ARCHIVES=(<sha256> file://shebang.c)`, `gcc -static`). Static, it needs no `/sw/glibc` mounted, so the kernel can run it in any namespace or chroot. A `shebang-pass1` (host-build, `gcc-pass1` against `glibc-pass1`, whose `glob` and `execvpe` already understand `GLOB_PATHS`) gives the chroot its handler right after the cross-toolchain exists; host-build packages run on the host, which has its own `/bin/sh`, and swctl already bind-mounts bash at `/sw/bash/bin/bash` there, so no handler is needed before that. That likely makes the bash-shim stage 1 below unnecessary.
              - **Registration (2026-11-20).** The rule names `/sw/shebang/bin/shebang` without `F`, so the kernel resolves it at exec time in the caller's mount namespace, and runs whichever finder is mounted there: the package itself, since `/sw` is mounted before swctl chroots and before boot hands over to init. Who writes the rule depends on where we are:
                - *Booted Fluffy, under systemd:* systemd does it. The `shebang` package ships `/sw/shebang/lib/binfmt.d/shebang.conf`; `systemd-binfmt` finds it through Fluffy's `CONF_PATHS` (`/etc`, `/run`, then `/sw/*/etc` and `/sw/*/lib`, from systemd's Fluffy patch), and `/etc/binfmt.d/shebang.conf` can override or mask it. Anything that runs a `#!` script before `systemd-binfmt.service` gets the kernel's literal behaviour, so nothing that early may depend on it.
                - *Cross-compiling (swctl):* swctl does it by hand. Setting up the chroot's namespace, after `/sw` is mounted, it mounts its own `binfmt_misc` (per user namespace since Linux 6.7) and writes the `#!` rule; `shebang-pass1` serves CROSS builds, `shebang` native ones.
              - **Two-Stage Bootstrap (`host /bin/bash` Shim → Native C `shebang` Binary)** (earlier plan; see the static design above):
                1. **Stage 1 (`host-build` Bootstrap Placeholder)**: On the host (where `swctl` already expands `/sw/*/bin` into explicit `PATH` entries so no `PATH` globbing is needed yet), `swctl` bind-mounts the host's `/bin/bash` ELF binary to `/sw/shebang/bin/shebang` with a tiny `BASH_ENV` hook. Because `/bin/bash` is an ELF binary (`\x7fELF`), `binfmt_misc` does not recurse on `#!`; when invoked on a script, `bash` sources `$BASH_ENV`, inspects line 1 of `$0`, executes plain `#!bash`/`#!sh` scripts directly in-process (treating line 1 as a `#` comment), and uses `BASH_ENV= exec <interp> "$0" "$@"` to dispatch flagged (`#!bash -e`) or non-shell (`#!perl -w`, `#!gawk -f`) scripts via normal `PATH` lookup.
                2. **Stage 2 (`cross-build` / `fluffy-build` Native C Handler)**: Once the cross-toolchain (`gcc-pass1` + `glibc-pass1`) is built, a tiny, zero-overhead native C `shebang` binary is cross-compiled against Fluffy's glob-aware `glibc` (`execvp`) and packaged at `/sw/shebang/bin/shebang`. Entering the chroot mounts `/sw/shebang` at the exact same `/sw/shebang/bin/shebang` path already registered in `binfmt_misc`, handing off seamlessly from the host bash placeholder to the native C binary.
            - **GNU `make` Default Shell (`default_shell = "bash"` / `SHELL = bash`) & `find_in_given_path` Wildcard `PATH`**:
              - In `make-4.4.1/src/job.c`, `default_shell` is hardcoded to `"/bin/sh"`, and when `USE_POSIX_SPAWN` is enabled (lines 2450–2460), `make` does not call `posix_spawnp()` (because `glibc`'s `execvpe`/`posix_spawnp` reads `getenv("PATH")` from the parent's `environ` rather than `child->environment`). Instead, `make` calls gnulib's `find_in_given_path(argv[0], p, NULL, 0)` (`lib/findprog-in.c`) before `posix_spawn()`.
              - Because gnulib's `find_in_given_path` splits `PATH` on `:` without expanding `/sw/*/bin`, relative command names (fast-path `touch`, `printf`, or `argv[0] = "bash"` when `SHELL = bash`) fail unless `SHELL` is an absolute path (`SHELL = /sw/bash/bin/bash`).
              - While `--disable-posix-spawn` falls back to `vfork()` + `environ = child->environment; execvp()` (which uses `glibc`'s wildcard `PATH`), it has the downside that missing commands (`ENOENT`) `vfork()` first and invoke `OSS(error, ...)` (`gettext`/`stdio`) inside the `vfork()` child while sharing the parent's heap, and skips `posix_spawn`'s dedicated stack and full signal masking.
              - **Fix for Chapter 8 `make`**: Set `default_shell = "bash"` in `src/job.c` and teach `find_in_given_path` (`lib/findprog-in.c`) to expand wildcard `PATH` entries via `glob()`. That keeps `USE_POSIX_SPAWN` enabled while making both `SHELL = bash` and Makefiles that omit `SHELL` altogether work out of the box via `/sw/*/bin`.
            - **Perl `File::Spec::Unix::path()` Wildcard `PATH` Expansion (`dist/PathTools/lib/File/Spec/Unix.pm`)**:
              - In Perl's standard library, `File::Spec->path()` (`File::Spec::Unix::path`) is the canonical function used by `IPC::Cmd::can_run()`, `ExtUtils::MakeMaker` (`maybe_command`), `CPAN`, and downstream consumers like OpenSSL's `./config` (`OpenSSL::config`) to iterate `$ENV{PATH}` directories.
              - Upstream `File::Spec::Unix::path` simply runs `split(':', $ENV{PATH}, -1)`, returning the literal string `"/sw/*/bin"`, which fails `-d $dir` checks in callers.
              - **TODO for Next `perl` Pass**: Patch `File::Spec::Unix::path` in `dist/PathTools/lib/File/Spec/Unix.pm` to expand wildcard `PATH` entries (using pure-Perl `opendir`/`readdir` so it works even inside `miniperl` before the `File::Glob` XS module is built), making `File::Spec->path()` and `IPC::Cmd::can_run()` work transparently across all Perl scripts without per-package overrides.
            - **Eliminating Explicit `/sw/<pkg>/bin/<prog>` Overrides (First-Class `PATH` Honoring)**:
              - **Architectural Imperative**: As much as possible, stop requiring build recipes to configure tools with explicit paths like `/sw/<pkg>/bin/<tool>` (e.g. `HASHBANGPERL=/sw/perl/bin/perl`, `PKG_CONFIG=/sw/coreutils/bin/true`, `autosetup_tclsh=/sw/tcl/bin/tclsh`). Build systems and packages must honor `$PATH` and resolve tools (`perl`, `tclsh`, `python3`, `true`, `sh`, `cc`) dynamically from the environment.
              - **Why Upstream Configures Currently Demand Absolute Paths**:
                1. *Interpreted `PATH` Scanners*: Scripts in Tcl (`autosetup`), Python (`shutil.which`), Perl (`File::Spec->path`), or gnulib (`findprog-in`) manually split `$PATH` on `:` and test each item with `stat`/`access(2)`, failing on `/sw/*/bin`.
                2. *Baking Shebangs into Generated Scripts*: Tools like OpenSSL or Automake resolve an interpreter during `./configure` specifically to write `#!$PATH_TO_PERL` into installed scripts.
              - **The Unified Path-Honoring Strategy**:
                1. *Runtime `which`/`path` Patches*: Teach each core language runtime's path-resolution primitive (Perl `File::Spec::Unix::path`, Python `shutil.which`, Tcl `TclpFindExecutable` / `split-path`, Gnulib `findprog-in`) to expand wildcard `$PATH` elements via `glob()`.
                2. *Path-Resolving Shebangs (`binfmt_misc`)*: With kernel-level `binfmt_misc` resolving shebangs via `$PATH` (`execvp`), installed scripts can simply use `#!perl`, `#!bash`, or `#!python3` instead of hardcoding `/sw/<pkg>/bin/<tool>`.
                3. *Global Autoconf Site Defaults (`CONFIG_SITE`)*: Provide a system-level `config.site` that pre-sets standard tool variables (`PERL=perl`, `AWK=gawk`, `SED=sed`, `PKG_CONFIG=true`) as bare command names rather than absolute filesystem paths, ensuring downstream Makefiles invoke tools through the active `$PATH`.
       - Shell defaults in `paths.h` and `system.c`: `_PATH_DEFPATH` defaults to `"/sw/*/bin"`, `_PATH_STDPATH` to `"/sw/*/bin"` (no `sbin`), and `_PATH_BSHELL` / `SHELL_PATH` to `"/sw/bash/bin/sh"` (the `sh -> bash` link that `sw/bash` and `sw/bash-pass1` install), so `system()` and `popen()` run bash in POSIX mode without `/bin/sh`.
     - **Dynamic Linker (`ld.so`)**: Iterates `/sw/*/lib` (`_dl_init_paths` in `elf/dl-load.c`) to resolve shared libraries dynamically at runtime.
     - **Final Pass Toolchain Vision (Glibc & GCC Native Wildcard Inclusion)**:
       - **GCC Preprocessor (`cppdefault.cc`)**: In the final native pass, patch GCC's include directory search logic to natively understand `/sw/*/include` (and `/sw/*/include/c++/<ver>`) instead of hardcoding `/usr/include`. GCC's CPP will discover and include headers across all mounted packages without passing a single `-I` flag.
       - **Linker (`binutils` `ld`) & Specs**: Set default library search paths to `/sw/*/lib` instead of `/usr/lib` or `/lib`.
         - **Dynamic Wildcard `SEARCH_DIR` in Binutils Linker Scripts**: `--with-lib-path='=/sw/*/lib'` (single-quoted so the build shell never expands it; `genscripts.sh` copies it verbatim, and the explicit `=` makes it sysroot-relative) embeds literal `SEARCH_DIR("=/sw/*/lib")` in the default ldscripts, allowing `ldfile.c` to dynamically expand `/sw/*/lib` via `glob()` at runtime and register all `/sw/<pkg>/lib` with `cmdline=false`. This ensures `ldelf.c` automatically resolves both direct `-l<name>` libraries and indirect `DT_NEEDED` dependencies (e.g. `libncursesw.so.6` needed by `libreadline.so`) without requiring `-rpath-link` or explicit `-L` flags.
       - **Zero `-I`/`-L` Flags & Deprecation of `pkg-config`**: Because GCC, LD, and LD.SO dynamically iterate all `/sw/*/{include,lib}`, packages built for Fluffy never need `-I` or `-L` directory path flags or `pkg-config` path overrides. Upstream packages link against external libraries simply with `-l<name>`. (`pkg-config` is back as `pkgconf`, which searches `/sw/*` and strips `/sw/*/{include,lib}` as system directories, so this stays true. See "`pkgconf`".)
     - **Systemd Unit Files (`/sw/*/lib/systemd/system`)**: `systemd` (`lookup_paths_init` in `sd-path/path-lookup.c`) iterates `/sw/*/lib/systemd/system` (and `/sw/*/lib/systemd/user`) so services install their own `.service` / `.socket` files directly in `/sw/<pkg>/lib/systemd/system/` (via a heredoc or local file in `INSTALL()`), eliminating any need for external meta-packages like `blfs-systemd-units`.
     - **General-Purpose Wildcard Support (Configure `/sw/*`, Never Hardcode `/sw/` in C Source)**:
       - **Architectural Rule**: C source patches to upstream packages must **never** hardcode Fluffy-specific directory names like `"/sw"` or `"/lib"` or custom `scandir("/sw", ...)` loops. Instead, upstream code is patched to support general-purpose glob/wildcard expansion in its standard configuration paths, and `/sw/*/bin`, `/sw/*/lib`, `/sw/*/include` are passed in via configuration (`configparms` `user-defined-trusted-dirs`, `configure` flags, `paths.h`, `STANDARD_STARTFILE_PREFIX`, `NATIVE_SYSTEM_HEADER_DIR`, `PATH`).
       - For example, in `glibc` (`elf/dl-load.c`), `SYSTEM_DIRS` receives `/sw/*/lib/` via `user-defined-trusted-dirs=/sw/*/lib` in `configparms`, and `_dl_init_paths` / `is_trusted_path_normalize` expand wildcard entries in `system_dirs` generically (just like `binutils` `ldfile.c` calls `glob()` on `LIB_PATH=/sw/*/lib` and `bash` calls `shell_glob_filename` on `PATH=/sw/*/bin`).
       - Similarly, `gcc` (`gcc.cc`, `incpath.cc`, `cppdefault.cc`) should expand wildcards in configured `STANDARD_STARTFILE_PREFIX`, `STANDARD_EXEC_PREFIX`, and `NATIVE_SYSTEM_HEADER_DIR` (`--with-native-system-header-dir=/sw/*/include`) via `glob()` rather than hardcoding `scandir("/sw")`.
     - **Universal `<glob.h>` Primitive, Language Runtime Delegation & `FSWC` SquashFS Cache (`glibc`)**:
       - `ldconfig` and `USE_LDCONFIG` (`ld.so.cache`) are completely disabled (`use_ldconfig=no`) in `glibc`. Instead of subsystem-specific caches or leaked userland helpers, POSIX `<glob.h>` and `<fnmatch.h>` in `glibc` serve as Fluffy's single universal late-binding primitive across `ld.so`, `execvpe`/`posix_spawnp`, `gcc`/`binutils`, shells (`bash`, `readline`), language runtimes (`python`, `perl`, `tcl`), and stateless-`/etc` consumers (`systemd`, `kmod`, `dbus`, `util-linux`, `man-db`, `openssl`, `curl`, etc.).
       - Custom `<glob.h>` / `<fnmatch.h>` flags (`GLOB_KEEP_SLASHES`, `GLOB_PATHS`, `GLOB_EXTMATCH`, `GLOB_CASEFOLD`, `GLOB_SKIPDOTS`, `GLOB_GLOBSTAR`, `GLOB_DOTDOT`, `FNM_DOTDOT`), language runtime delegation, the internal `FSWC` cache (v6: a sorted per-user, per-namespace path index read through `glob()`'s `GLOB_ALTDIRFUNC` hooks; `GLIBC_TUNABLES=glibc.fswc.enable`), its design history, per-package test suite requirements, and the phased implementation roadmap are specified in **[GLOB.md](GLOB.md)**.
     - **TODO: Cross-Package File Collision Vetting Tool (`<relpath>\t<pkg>`)**:
       - Because `/sw/*` late binding resolves matches in alphabetical (`alphasort`) package order, two packages accidentally shipping the same relative file path (binary, header, shared library, unit, or config default) would silently shadow the alphabetically later package rather than failing loudly.

5. **Hermetic, Unprivileged Builds & Unified Tooling (`swctl build`, `swctl install`)**
   - **Developer Environment Convention (`direnv` & `sudo --preserve-env`)**:
     - Developer environments export `CROSS=1` and `FLUFFY` variables via `direnv`.
     - When invoking `swctl` under `sudo`, commands should use `sudo --preserve-env=CROSS,FLUFFY ./swctl build <pkg>` (or `swctl install <pkg>`) to preserve the caller's environment rather than prefixing `CROSS=1` manually.
   - **Folding `create` into `swctl` (`swctl build`)**:
     - All package building and recipe orchestration is unified under `swctl` (`swctl build <pkg...>` and `swctl install <pkg...>`), auto-prefixing `sw/` so package names are first-class identifiers (`swctl build glibc`, `swctl install gcc`).
     - **Registration as a Build Byproduct**: With `swctl build`, registration ceases to exist as a separate manual step. Upon completing `SQUASHFS`, `swctl build` automatically calculates the image SHA-256 checksum (`X-fluffy.image-checksum`), writes the `/sw/.build/fstab` entry (target `/sw/<pkg>`, `X-fluffy.needs`, `X-fluffy.recipe-checksum`, `X-fluffy.image-checksum`), and signs the `/sw/.build/fstab` manifest file in a single atomic transaction. The fstab file itself is the sole signed artifact.
   - **Recursive Recipe DAG Resolution, Direct Build Input Hashing (`format_recipe_mime`), Early Cutoff & Fixed-Point Cyclic Build Convergence**:
     - `swctl build <pkg...>` recursively walks the recipe files in `sw/` across `ON`, `NEEDS`, and `BUILD_NEEDS`.
     - **In-Memory Direct Build Input Hash (`format_recipe_mime`)**: Without mutating git-tracked `sw/<pkg>` files on disk, `format_recipe_mime` streams the raw `sw/<pkg>` recipe file, any sourced helper files (`pkg_includes`), and sorted `<dep>:<X-fluffy.image-checksum>` pairs for **direct** `$ON` + `BUILD_NEEDS` dependencies (`pkg_bneeds`) through `sha256sum`.
     - **Early Cutoff & Image Checksum Reuse**: Rebuilding a byte-identical `.squashfs` preserves `X-fluffy.image-checksum`. `SQUASHFS()` writes to `<pkg>-<ver>.squashfs.new`, and `register_entry` compares its SHA-256 against the existing `X-fluffy.image-checksum` in `/sw/.build/fstab`. If the newly built `.squashfs` is identical, `register_entry` preserves `X-fluffy.image-checksum` and updates `X-fluffy.recipe-checksum`, stopping the downstream rebuild cascade immediately.
     - **TODO: Self-Hosting Build Cycles (`ON=fluffy-build`, `glibc` ↔ `gcc`) & Fixed-Point Convergence**:
       - While runtime dependencies (`NEEDS` in `swctl install`) must form a strict DAG, a self-hosting native build system (`ON=fluffy-build`) inherently contains build-time cycles (Strongly Connected Components / SCCs): `glibc` needs `gcc` in `BUILD_NEEDS`, `gcc` needs `glibc` in `NEEDS`, and every `ON=fluffy-build` package depends on `fluffy-build` (including the packages that make up `fluffy-build`).
       - Because Fluffy combines bitwise reproducible builds with image checksum preservation (`register_entry`), `swctl build` can resolve cyclic build SCCs by iterating to a **cryptographic fixed point**:
         1. On Pass 1 of a cyclic SCC (e.g. `glibc` → `gcc`), `glibc` builds using the currently registered `gcc` ($G_0$), producing $C_1$, and `gcc` rebuilds against $C_1$.
         2. If `gcc` produces a byte-identical `.squashfs`, `register_entry` preserves $G_0$, so `glibc`'s `current_recipe_chk` immediately matches its `recorded_recipe_chk` (`X-fluffy.recipe-checksum`) and the cycle terminates in 1 pass.
         3. If `gcc`'s binary output changed ($G_1 \neq G_0$), `glibc`'s `current_recipe_chk` (which hashes $G_1$) differs from its `recorded_recipe_chk` (which hashed $G_0$), so Pass 2 rebuilds `glibc` with $G_1$ (and if needed, `gcc` with $C_2$) until every `X-fluffy.image-checksum` is preserved around the cycle and **every package in `/sw/.build/fstab` simultaneously satisfies `recorded_recipe_chk == current_recipe_chk`**.
         4. **Bounded Convergence Guard**: If a cyclic SCC fails to reach a fixed point within a small bounded number of passes (e.g. `MAX_CYCLE_PASSES=3`, analogous to GCC's 3-stage bootstrap comparison), `swctl build` fails with a fatal diagnostic naming the non-converging package(s) whose `.squashfs` output is failing to stabilize (automatically catching any build nondeterminism).
   - **Unified `BUILD_NEEDS` Architecture & Strict Isolation (Build-Time vs. Runtime)**:
     - Dependency declarations across all recipes are consolidated into a clean two-tier model: `NEEDS` (runtime dependencies) and `BUILD_NEEDS` (all tools required across `MAKE`, `CHECK`, and `INSTALL`).
     - **Strict Sandbox Mount Isolation (`BUILD_NEEDS` Only)**:
       - `NEEDS` represents runtime-only dependencies of the packaged software. It is **never mounted** during `MAKE`, `CHECK`, or `INSTALL`.
       - Build phases only mount `BUILD_NEEDS` (and the runtime dependencies those build tools themselves need to execute). Leaking runtime `NEEDS` into the build sandbox is eliminated, ensuring that a package cannot silently link against or inspect undeclared build requirements.
   - **Sound Early Cutoff via Direct `BUILD_NEEDS` + `$ON` Image Hashing (No Dependency Trimming)**:
     - `X-fluffy.recipe-checksum` locks strictly against the recipe definition, any included files, and the image checksums (`X-fluffy.image-checksum`) of **direct** `BUILD_NEEDS` + `$ON` images only.
     - **No `NEEDS` in Recipe Checksum**: A runtime-only dependency change (e.g. updating `ca-certificates` or `shadow`) never alters compiled build outputs and must never trigger a rebuild.
     - **No Transitive Expansion & No Transitive Trimming**: To enable true early cutoff, the recipe checksum does not expand transitive dependencies—and recipes must **never** trim direct dependencies just because another dependency happens to pull them in transitively. If an upstream dependency $Z$ changes, but intermediate package $Y \in \text{BUILD\_NEEDS}$ rebuilds to an identical squashfs image, downstream package $X$ skips recompilation entirely; therefore, if $X$ directly depends on $Z$, $X$ must list $Z$ explicitly in its own immediate dependencies so changes to $Z$ are tracked accurately for $X$.
   - **Multipart MIME Serialization for Recipe Checksums (`source X`)**:
     - Recipes execute as plain, untouched Bash at runtime (`source "$inc"` is just `builtin source`).
     - For modification detection and recipe checksumming, `swctl` serializes the recipe, all sourced snippets, and direct image checksums into a canonical multipart MIME envelope (RFC 2046) with explicit boundaries, preventing ad-hoc delimiter collisions and providing an inspectable, self-contained record of the build recipe inputs.
   - **Declarative Direct Dependency Contract (The Recipe Honor System)**:
     - As in Arch (`makedepends`), Debian (`Build-Depends`), and Alpine (`makedepends`), dependency declaration is fundamentally a declarative recipe contract.
     - If package $X$ directly consumes APIs, headers, tools, or libraries from package $Y$, the recipe author declares $Y$ in `BUILD_NEEDS`.
     - If package $X$ only uses $Y$, and $Y` internally uses $Z$ as a transitive implementation detail, $X$ does *not* declare $Z$.
     - By keeping dependency declarations strictly direct, early cutoff functions as intended: if $Z$ changes, $Y$ rebuilds; if $Y$ produces an identical squashfs image, $X$ skips recompilation entirely.
     - Sandbox isolation (never mounting runtime `NEEDS` during `MAKE`) naturally prevents the most common class of undeclared dependencies without requiring complex language-specific source scanners or kernel tracing.
   - **Explicit `CROSS=1` Bootstrap vs. Native Self-Hosting (`ON=fluffy-build`)**:
      - **Runtime `NEEDS=(...)` is Strictly Invariant**:
        - A final package's runtime contract never varies between bootstrap and native modes. `NEEDS=(...)` is always 100% composed of final packages (`glibc`, `attr`, `acl`, `libxcrypt`, etc.) from day one.
        - Neither `-pass1` nor `-pass2` packages ever appear in a final package's runtime `NEEDS` or in `X-fluffy.needs` in `/sw/.build/fstab`.
      - **Explicit `CROSS=1` Build-Tool Branching**:
        - Scaffolding (`ON`, `BUILD_NEEDS`) branches cleanly on `if test -v CROSS`.
        - The default mode is native (`ON=fluffy-build`), avoiding any runtime filesystem/fstab autodetection overhead.
        - Cross-building during initial bootstrap is summoned explicitly via `CROSS=1` (e.g. `sudo --preserve-env=FLUFFY,CROSS ./swctl build <pkg>`), switching `$ON` to `cross-build` and `BUILD_NEEDS` to `*-pass1` / `gcc-pass2`.
      - **Zero Git Churn & Automatic Invalidation**:
        - Keeping both scaffolding closures inside the same recipe file avoids branch juggling or local file edits.
        - Because `format_recipe_mime` hashes `$ON` and the image checksums of direct build dependencies, `swctl build` automatically knows when a package was built against bootstrap tools vs native tools, enabling seamless fixed-point convergence once `fluffy-build` is assembled.
   - **Distro-as-Build-Environment, Remote Repositories (`/etc/sw/repositories`), Trust Store (`/etc/sw/*.pub`) & Parallel Bottle Prefetch (`curl -Z`)**:
     - **Core Philosophy — A Distribution That Is Secretly a Build Environment**:
       - Fluffy does not have a separate "binary package manager" vs. "source build system". A Fluffy installation is simply a `swctl build` environment backed by signed binary bottle caches, and the installed system universe is managed by building/mounting a top-level `world` (or `local`) pseudopackage.
       - Because every `fstab` entry records `X-fluffy.recipe-checksum` (the SHA-256 of the RFC 2046 multipart MIME envelope containing the recipe, any sourced includes, and sorted `<dep>:<X-fluffy.image-checksum>` pairs across direct `BUILD_NEEDS` + `$ON` images), changing any recipe, include, or direct build dependency automatically invalidates `X-fluffy.recipe-checksum` downstream while preserving early cutoff across untouched dependencies.
     - **Trust Store (`/etc/sw/*.pub`) & Repository Sources (`/etc/sw/repositories`)**:
       - `/etc/sw/*.pub` (overlaid on `/sw/*/etc/sw/*.pub`) holds trusted `signify` public keys.
       - `/etc/sw/repositories` configures one or more remote repository URLs serving signed `fstab` manifests and `.squashfs` bottles (supporting multiple merged repository sources).
     - **Upfront DAG Resolution & Parallel Bottle Prefetching via `curl --parallel` (`-Z`)**:
       - When `swctl build <pkg...>` calculates the topological dependency closure (`${order[@]}`), it can first fetch and verify the remote signed `fstab` manifest(s) from `/etc/sw/repositories`.
       - Walking `${order[@]}` in topological order in memory, `swctl` compares each package's computed `current_recipe_chk` against both the local `/sw/.build/fstab` and the remote `fstab`(s) (adopting the remote `X-fluffy.image-checksum` whenever a remote entry matches `current_recipe_chk`).
       - Before running a single local build, `swctl` knows the exact set of missing or outdated packages in the closure that have valid prebuilt `.squashfs` bottles upstream, downloads **all** of them concurrently in one shot via `curl --parallel` (`-Z`), verifies the signed manifest against `/etc/sw/*.pub` and compares image SHA-256 hashes, updates `/sw/.build/fstab`, and then kicks off local builds only for the remaining locally-modified packages.
     - **Binary Bottles (GitHub Packages / GHCR / Download Mirrors)**:
       - `ON=host-build` and `ON=cross-build` recipes (`*-pass1`, `*-pass2`) are host-dependent and stored as **private** packages solely for CI reuse (avoiding cache eviction), whereas `ON=fluffy-build` packages are **public** portable bottles (which have free, unlimited storage and bandwidth on `ghcr.io`).
       - **OCI Artifact Layout on `ghcr.io` (Homebrew-Style Arbitrary Files)**:
         - Packages are stored on `ghcr.io` as standard OCI Artifacts: **1 package per `.squashfs`** and **1 package for the `fstab` manifest**, scoped per branch (e.g., tagged by branch and overwritten when changed).
         - Because `ghcr.io` stores each uploaded file as a content-addressed blob whose layer descriptor in the ~1 KB OCI manifest JSON embeds its exact `sha256` digest (`layers[0].digest`), `swctl` can query a package's remote `.squashfs` `sha256` checksum via a lightweight manifest fetch (`GET /v2/<owner>/<pkg>/manifests/<tag>`) independently of downloading the `.squashfs` blob itself, and `ghcr.io` automatically deduplicates identical blobs on the backend.
     - **CI/CD & `swctl` Registry Workflow (`fstab` Sync, Lazy Prerequisite Fetch & Atomic Publish)**:
       - **1. Fetch Latest Branch `fstab`**:
         - At the start of a run, `swctl` downloads the latest signed `fstab` package for the current branch (keeping a copy of the pre-build `fstab` to diff against at publish time).
       - **2. Existence-Verified `UP-TO-DATE` Check (`build` vs. `install` Semantics)**:
         - Walking `plan_pkgs` in topological `order`, `swctl build` computes `current_recipe_chk` (`format_recipe_mime`, which hashes the recipe, sourced includes, and direct `ON` + `BUILD_NEEDS` `X-fluffy.image-checksum` values) and compares it against `X-fluffy.recipe-checksum` in `fstab`.
         - **Build vs. Install**: During `swctl build`, a package's `.squashfs` file does *not* need to sit on local disk if nothing is mounting it, **provided** the `.squashfs` matching `X-fluffy.image-checksum` is verified to exist (either locally in `/sw/` or in its corresponding `ghcr.io` package manifest).
         - By verifying that `X-fluffy.image-checksum` matches the sole image digest in `ghcr.io`'s manifest for every `UP-TO-DATE` entry in `fstab`, `swctl build` guarantees that a complete, self-consistent set of `.squashfs` images exists in the registry for `swctl install`.
         - On a cache miss (`recorded_recipe_chk != current_recipe_chk`, or the `.squashfs` is absent/mismatched both locally and in `ghcr.io`), `swctl` rebuilds the package (recursively fetching or rebuilding its dependencies).
       - **3. Up-Front `ensure_prerequisites` (Outside `CLONE_NEWNET` Lockdown)**:
         - Because `lockdown_exec` immediately enters an air-gapped network namespace (`CLONE_NEWNET`) and the `FLUFFY` chroot mounts `$ON` before executing inside the sandbox, all network downloads for a package build happen up-front on the host via `ensure_prerequisites`:
           1. **Recursive `.squashfs` Dependencies (`$ON` + `BUILD_NEEDS` + Transitive `X-fluffy.needs`)**: Walks the mount dependency closure via `dfs`. For any required `.squashfs` not already present and checksum-verified in `/sw/`, `swctl` downloads the blob from `ghcr.io` and verifies its `sha256` against `X-fluffy.image-checksum`. (This same helper powers lazy `.squashfs` fetching for `swctl install <pkg...>`).
           2. **Source `ARCHIVES`**: Downloads and verifies all `ARCHIVES[@]` tarballs/files into `work/archives/`.
         - Consolidating both `.squashfs` and `ARCHIVES` fetches into `ensure_prerequisites` keeps `lockdown_exec` strictly offline, avoids needing `ghcr.io` credentials or CA certs inside the chroot, and makes a future air-gapped/offline prefetch mode (`swctl fetch`) trivial.
       - **4. Atomic Two-Phase Publish (Changed `.squashfs` Images First, `fstab` Last)**:
         - Upon build completion, comparing the new `/sw/.build/fstab` against the pre-build `fstab` (or remote manifest digests) identifies every package whose `X-fluffy.image-checksum` changed.
         - CI first uploads all changed `.squashfs` images to their corresponding branch packages in `ghcr.io` (and prunes untagged versions on private packages to avoid storage quota bloat).
         - Only after **all** changed `.squashfs` uploads succeed is the newly signed `fstab` uploaded to its branch package—acting as an atomic commit pointer so consumers never observe an `fstab` referencing an unuploaded `.squashfs`.
       - **CI Pipeline via `sw/world` Pseudopackage (`swctl build world`)**:
         - `sw/world` is a standard pseudopackage (`ON=host-build`, `VERSION=1.0`, `NEEDS=(...)` with no build steps, producing `world-1.0.squashfs` and identical in all other ways to any other package) that explicitly lists every final package on the Fluffy image according to Chapter 8 of Linux From Scratch (untrimmed).
         - With caching, prerequisite fetching, and publishing integrated into `swctl`, the entire CI pipeline on push to `main` is simply `swctl build world` (and installing the full base system is `swctl install world`).
         - **Dev (`SNAPSHOT`) vs. Release Channels & Immutable Release Versions (`fluffy0`, `fluffy1`)**:
           - Dev/main builds and tagged releases are separated Maven-style (`SNAPSHOT` vs. release manifests/tags) so experimental rebuilds don't overwrite release bottles.
           - **Release Immutability Guard & Package Revisions**: On release builds, publishing over any existing package version is a hard error. Before publishing *any* artifact, CI checks the entire publish set and fails immediately if any rebuilt package (`X-fluffy.recipe-checksum` changed) still has a version/filename that already exists in the release registry—which always means a version bump was forgotten.
           - To support recipe/patch updates without changing upstream `$VERSION` (used in `ARCHIVES` URLs), recipes support Debian/Ubuntu-style package revisions (`fluffy0`, `fluffy1`, etc., e.g. `<pkg>-<version>-fluffy0.squashfs`).
         - **Debian-Style Reproducible Builds & Early Cutoff (Avoiding Mass Rebuild Cascades)**:
           - In purely input-addressed systems (Nix/Guix), changing an upstream recipe like `glibc` alters input hashes and forces blind rebuild cascades across every downstream package, even when compiled output binaries would be bit-for-bit identical.
           - By enforcing Debian-style bitwise reproducible builds (`SOURCE_DATE_EPOCH=0`, deterministic squashfs creation, normalized timestamps and filesystem ordering), Fluffy employs an **early cutoff** strategy directly in `swctl`: when an upstream dependency changes and a downstream package is rebuilt, `register_entry` compares `.squashfs.new` against the existing `X-fluffy.image-checksum`; if they are identical, it preserves `X-fluffy.image-checksum` so all further downstream packages see an unchanged `format_recipe_mime` hash and the rebuild cascade stops immediately.
         - **SquashFS vs. Object-Level Hashing**: Unlike OSTree or Git, which hash individual uncompressed files, Fluffy hashes the `.squashfs` image directly with SHA-256. A change to `zstd` compression heuristics or `mksquashfs` block layout will change the `.squashfs` SHA-256 even if uncompressed files are identical. However, because `zstd` and `squashfs-tools` belong to `cross-build` / `fluffy-build`, any change to the compression toolchain automatically triggers a system rebuild anyway—so within a stable toolchain generation, deterministic `mksquashfs` is completely sufficient without needing an extra object-hashing layer.
     - **Native OS Detection (`/etc/os-release`) & Local User Packages (`sw/local`)**:
       - Using `/etc/os-release` (`ID=fluffy`) and `$ON`, `swctl` knows when it is running natively on Fluffy Linux vs. bootstrapping from a foreign host, ensuring users on Fluffy never re-trigger `pass1`/`pass2` cross-compilation because `ON=fluffy-build` packages are self-contained.
       - Users can define local packages and even a `sw/local` pseudopackage (`NEEDS=(world userpkg1 userpkg2)`), where `world` resolves from signed upstream bottles while `userpkg1` and `userpkg2` build locally.
     - **Setuid Embedded-Script `swctl` Binary, `build` Group & User vs. System Squashfs Separation**:
       - Because the Linux kernel ignores the `setuid` bit on `#!` scripts, `swctl` can be packaged as a dedicated setuid binary built from a special-purpose `bash` (with the `swctl` script embedded in `.rodata` and `-c` / interactive flags disabled) or a small C wrapper.
       - A `build` group and separate storage/namespace boundaries between system squashfs images (requiring `CAP_SYS_ADMIN` / system install privileges) and user-built squashfs images allow unprivileged users to run `swctl build` out of their own home-directory recipe clones (and even drop into a shell with a custom `fstab` software set) without granting them unrestricted root access to the system.

6. **The Manifest & System Installer Architecture (`/sw/.build/fstab`, Remote `fstab`s & `/etc/fluffy/fstab`)**
   - **1. `/sw/.build/fstab` — The Local Build & Available Package Index**:
     - Records every locally built or staged `.squashfs` image available in `/sw/` (including `/builder` harness packages, `*-pass1`, `*-pass2`, build-only libraries, and uninstalled packages), formatted as an `fstab(5)` file (unsigned since 2026-11-20; see "Signing removed" below):
       ```fstab
       /sw/foo-1.23.squashfs /sw/foo squashfs X-mount.mkdir,X-fluffy.image-checksum=<sha256>,X-fluffy.needs="bar,baz",X-fluffy.recipe-checksum=<sha256> 0 0
       /sw/bar-2.0.squashfs /sw/bar squashfs X-mount.mkdir,X-fluffy.image-checksum=<sha256>,X-fluffy.needs="bar,baz",X-fluffy.recipe-checksum=<sha256> 0 0
       ```
   - **2. Remote Source `fstab` Manifest(s) — Signed Upstream Bottle Indexes**:
     - Fetched from configured remote repositories (`/etc/sw/repositories`) and cryptographically verified against trusted `signify` public keys (`/etc/sw/*.pub` / `/sw/*/etc/sw/*.pub`) before any bottle metadata or `.squashfs` digest is trusted.
   - **3. `/etc/fluffy/fstab` — The Currently Installed System Manifest**:
     - Records the exact topological set of `.squashfs` packages actually **installed** in the active system generation.
     - Free of duplicate mountpoint collisions (`*-pass1` vs. final packages) and build-only clutter.
     - Because it lives under `/etc` on the Btrfs root subvolume, Btrfs system snapshots automatically capture `/etc/fluffy/fstab`, `/etc` configuration, and the referenced `.squashfs` extents together as a single atomic generation.
   - **Why `fstab(5)` as the Manifest Format Is So Powerful**:
     - **Directly mountable by standard tools**: `libmount`, `mount -a -T`, and `systemd-fstab-generator` treat `#` as a comment line by default. No stripping or pre-processing is needed to use an `fstab` as a mount table.
     - **Standard Userspace Options (`X-appname.option`)**: In accordance with the `mount(8)` and `libmount` standard specification, all user-space / application-specific mount options are prefixed with `X-<appname>.<option>` without leading hyphens:
       - `X-fluffy.image-checksum=<sha256>`: package image SHA-256 checksum (preserved across rebuilds when the new `.squashfs` is byte-identical).
       - `X-fluffy.needs="<dep1>,<dep2>"`: comma-separated list of runtime dependency packages.
       - `X-fluffy.recipe-checksum=<sha256>`: sha256 checksum of the multipart MIME envelope (`format_recipe_mime`) containing `sw/<pkg>`, any sourced includes, and the sorted `<dep>:<X-fluffy.image-checksum>` pairs of its direct `$ON` + `BUILD_NEEDS` dependencies, recording both recipe and dependency provenance without mutating recipe files on disk.
     - *For published manifests, once downloads exist (the local build fstab is unsigned since 2026-11-20):*
     - **Compact Ed25519 signatures**: Raw Ed25519 signatures are exactly 64 bytes (88 base64 characters; 100 characters in OpenBSD signify format)—no massive ASCII armor blocks or multi-kilobyte RSA blobs.
     - **Single-file verification**: The signature on line 1 covers lines 2 through EOF. Verifying line 1 against the trusted public key validates the entire repository index in one shot (all package filenames, mountpoints, squashfs image checksums, and dependency closures) without needing separate detached `.sig` files or per-package signatures:
       ```bash
       sig=$(sed -n '1s/^# fluffy\.signature=//p' /sw/.build/fstab)
       # Verify lines 2..EOF against the embedded signature
       ```
     - **Trust Root / Bootstrap**: The distro release signing public key cannot live inside a package squashfs (which would be circular). Instead, it lives alongside the manifest at `/sw/.build/release.pub` (or embedded in the bootstrap script / `/init`), providing the root of trust from day one.
     - **In-process parsing & mounting**: `libmount` (`<libmount/libmount.h>` called via `ctypes.sh`) parses the manifest, resolves dependencies, checks options (`X-mount.mkdir`, `X-fluffy.image-checksum`, `X-fluffy.needs`, `X-fluffy.recipe-checksum`), and mounts the squashfs images directly in-process.

7. **Runtime State Separation (`/var/<pkg>`) & Dynamic Users**
   - Packages in `/sw/<pkg>` are strictly immutable, code/asset-only squashfs images packed with `-all-root` (everything owned by `root:root`).
   - Packages that require persistent mutable runtime state (databases, spools, caches) store it in `/var/<pkg>` (e.g. `/var/locate`, `/var/systemd`).
   - To avoid coordinating hardcoded static UIDs across package definitions at build time, runtime services run under dynamic users (e.g. `DynamicUser=yes` with `StateDirectory=` under systemd, or `sysusers.d` allocation at install/boot).
   - This ensures `/var/<pkg>` directories are mode `0700` and accessible only to that specific package's service, with zero UID baked into the package image itself.

9. **Snapshot-Backed Retention & Immediate Unlink Model (Zero Separate `prune` Daemon Needed)**
   - **Pre-Transaction Btrfs Snapshot + Immediate `unlink(2)` in Live `/sw`**:
     - Prior to applying an upgrade or package removal, the installer takes an atomic Btrfs snapshot of the system subvolume.
     - Once `/etc/fluffy/fstab` (and `/sw/.build/fstab` where applicable) is updated, superseded/unreferenced `.squashfs` files are `unlink(2)`ed immediately from the live `/sw/` directory rather than accumulating loose historical versions in `/sw/`.
   - **Why Immediate Unlink Is Double-Safe (Running Processes + Rollback)**:
     - **Running Processes (POSIX Refcounting)**: Standard Linux VFS/loop semantics keep an unlinked `.squashfs` inode's extents alive as long as any loop mount in any active process's private mount namespace (`CLONE_NEWNS`) still references it, freeing the blocks automatically the instant the last process exits (with zero `/proc/*/mountinfo` polling needed).
     - **System Rollbacks (Btrfs CoW Snapshots)**: Because the pre-install Btrfs snapshot shares the `.squashfs` data extents via Copy-on-Write, unlinking the old `.squashfs` in the live subvolume costs zero extra disk copies while preserving the exact bootable historical generation (`/etc/fluffy/fstab`, `/etc`, `/init`, and `/sw/*.squashfs`).
   - **Retention Policy Equals Snapshot Pruning**:
     - Keeping 30 days (or $N$ generations) of instant GRUB-bootable rollbacks—and reclaiming disk space afterward—reduces entirely to standard Btrfs snapshot retention (`btrfs subvolume delete`) rather than maintaining a custom package garbage collector.

10. **Boot Architecture: GRUB Direct-Mount, Kernel Squashfs & Static `/init`**
    - **Kernel & Modules in `/sw/linux`**:
      - The Linux kernel and its loadable kernel modules are packaged together in `/sw/linux-<version>.squashfs` and mounted at `/sw/linux`.
      - Modules live in `/sw/linux/lib/modules/<kernel-version>/`.
    - **GRUB Squashfs & Btrfs Native Direct-Mount**:
      - GRUB natively includes filesystem drivers for both Btrfs and Squashfs (`insmod btrfs`, `insmod squash4`).
      - GRUB mounts the Btrfs root filesystem, locates the active kernel squashfs (`/sw/linux-*.squashfs`), and mounts/reads the squashfs image directly on the fly.
      - GRUB streams the kernel (`vmlinuz`) directly into RAM from the `.squashfs` image without requiring any intermediate unpacking on disk or an initramfs.
    - **Zero-Initramfs Boot via Tiny Static `/init` on Btrfs Root**:
      - With `CONFIG_DEVTMPFS_MOUNT=y`, Btrfs, SquashFS (`CONFIG_SQUASHFS_ZSTD=y`), and Loop device support built into `vmlinuz`, the kernel mounts the Btrfs root filesystem directly and starts `/init` (a tiny statically linked C binary on `/`).
      - **Early Boot Sequence (Prior to `systemd`)**:
        1. Kernel mounts Btrfs `/` and `devtmpfs` on `/dev`, then executes static `/init` as PID 1.
        2. `/init` mounts `/etc/fstab` (if needed prior to systemd) and `/etc/fluffy/fstab` (the installed system squashfs mount table, loop-mounting each `/sw/<pkg>-<ver>.squashfs` onto `/sw/<pkg>`).
        3. `/init` calls `execv("/sw/systemd/lib/systemd/systemd", argv)` to hand off PID 1 to `systemd`.
    - **Zero-Hack PID 1 Startup**:
      - `systemd` starts with all dynamic libraries (`/sw/*/lib`), unit files (`/sw/*/lib/systemd/system`), and binaries (`/sw/*/bin`) already mounted and available in `/proc/1/ns/mnt`.
      - Kernel modules load directly from `/sw/linux/lib/modules/<version>`.
      - Zero package hooks run during boot; the system starts immediately with full consistency.

## Decision History & Working Rules

Recovered from earlier assistant sessions, so the reasoning survives. Quotes are the project owner's words. Glob and cache history lives in [GLOB.md](GLOB.md) §2.

### Why the Architecture Is Shaped This Way

- **SquashFS per package, not overlayfs.** "Overlayfs can only go so deep." Worse: "you have zero guarantees it'll be correct—what if the installer skips already present files?" Symlink farms are "verboten; we fix the source package via patching."
- **Late binding.** "It's okay if that *ends up* as a hardcoded reference but it shouldn't *start* as one… zero extra flags is the goal," so splitting or merging packages later just works. `pkg-config` was "verboten": libraries were found by `/sw/*/{include,lib}`, and extra flags travelled as `X-fluffy.cflags`/`X-fluffy.ldflags` in the fstab (`HAS_CFLAGS`/`HAS_LDFLAGS` in recipes). *Reversed 2026-11-18:* see "`pkgconf`" below. The zero-flags goal stays.
- **Namespaces.** "Software upgrades *never* affect a running program… sidesteps torn-install problems." Later: "support software installs without updates… make it so new namespace only needed on upgrades." That second decision is why no component may assume `/sw` is constant within a running process.
- **`swctl` runs inside the chroot** "because someday it MUST". It uses `ctypes.sh` (`call mount`, `call unshare`) rather than shelling out, keeping "the full flexibility of bash" while builds lose network access. The `host-build`/`cross-build`/`fluffy-build` pseudopackages are ordinary packages with no build steps, and still produce a squashfs. Every install goes to one `DESTDIR=/sw/.build/destdir`.
- **Rebuild model.** The recipe checksum covers the recipe, its direct `BUILD_NEEDS`, and the `ON` images, which is "not nix-level correct" and accepted as such. Hence "it is extremely important for our *direct* dependencies to be honest, or we may incorrectly skip rebuilds." `NEEDS` means "something at runtime will blow up if this is not present" and is never mounted during builds. "Final package versions should never NEEDS a -pass1 dependency." There is no `PREPARE_NEEDS` or `SQUASHFS_NEEDS`. `CROSS=1` is explicit with no autodetection, so the default stays non-cross. Reproducible builds give early cutoff by plain `cmp`.
- **The fstab is the package database.** One file "addresses three things: apt-get-like manifest, file validation, real fstab needs… dependency DAG." The only signature is over the whole fstab (`image-checksum` and `recipe-checksum` are per-entry options), and it is verified with `signify` before anything parses it. `/sw/.build` (keys, fstab) is hidden behind a tmpfs in unprivileged build phases, so no package, `glibc` included, may depend on reading it. A mount with missing dependencies is an error that lists every missing dependency and mounts nothing. There are two fstabs: `/etc/fluffy/fstab` (installed) and `/sw/.build/fstab` (available).
- **Stateless `/etc` evolved** from versioned `/etc` with btrfs snapshots, through `fluffy-init`/`fluffy-upsert` with per-package `/etc/<pkg>`, to "programs place their static config in /sw/*/etc. user config goes in /etc… user settings 'win'." Packages have "zero pre/post install/uninstall" hooks, "pushed as far as I can". Still open from that discussion: UID overlap (now `mkuid.sh`), and the fact that network config "can't live in a package".
- **passN packages are host-dependent** and must never be distributed as downloads.
- **Distribution plan.** One container-registry package per squashfs plus one fstab "manifest" package. Changed images upload *before* the fstab (commit-pointer order), and tags are immutable. CI goal: "on push to main branch, 'swctl build world' the end." No dependency trimming: "trimming was an experiment and a mistake."
- **Boot.** A static `/init` in the btrfs root, no initramfs.
- **Hermeticity (open).** "I don't like that things can accidentally depend on my build dependencies." Ideas so far: a separate `/builder/*` path, and an ACCEPTANCE phase that monitors path accesses.

### Idea: Kernel Support for Wildcard Lookup (2026-11-18, not planned)

The question Fluffy asks is "how far can I push squashfs packages using glob() as the resolution primitive instead of symlink farms". Success is staying within 10–20% of plain-path performance. FSWC is the userspace approximation; the owner's theory is that the caching and invalidation ultimately belong in the kernel. A design sketch, for if that ever becomes possible:

- **Two globs, two kernel roles.**
  - **The restricted search list** (ld.so and `execvp`: malloc-free, one whole-`*` component) is small enough for the kernel to *answer*. Something like an `openat2` resolve flag (`RESOLVE_GLOB_FIRST`) would open the first match of `/sw/*/lib/NAME` in byte order, walking candidates under RCU against the dentry cache. One syscall replaces ld.so's search loop, and `PATH` search everywhere has the same shape, so the idea is not Fluffy-specific.
  - **The expressive `glob()`** (extglob, braces, `**`, case-folding, collation; the one swapped in for Python, Perl and Tcl) stays in glibc: matching rules are policy. Matching is cheap; enumerating directories and knowing whether a cached listing is still valid are not. So the kernel would only *accelerate* it, by saying exactly when a directory changed, and FSWC would keep the listings and do all matching.
- **Track damage, not freshness.** "There's no sense keeping an index nice and updated if nobody is asking about it… the real question is 'is the index damaged, and if so, where'."
  - Directories carry an in-memory damage stamp, never stored on disk and paired with the boot ID. It works like a cascading mtime, Merkle-ish, meaning "something under here changed".
  - A global damage epoch advances only when someone queries. A write stamps its directory and walks up, stopping at the first ancestor already stamped this epoch. Writes between queries then cost about one step, with no hot counter at `/`.
  - Mounting and unmounting count as changes to the parent, so mounting `/sw/zlib` damages `/sw`.
  - A reader keeps the epoch its index was built at. "Damaged?" is one comparison at the top, and "where?" descends only into newer stamps, so the cost scales with the damage, not the tree.
  - A stamp means "may have changed": false positives are allowed, missed changes are not. Each reader keeps its own epoch.
  - It is damage tracking as in a compositor: nothing is repainted until a frame is wanted, and then only the damaged regions are.
  - A first version kept a per-directory "observed" bit so writes could stop propagating early. Advancing the epoch on queries gives the same early stop without the kernel knowing who is watching, and it keeps nothing per consumer.
- **Validity is per lookup, not per index.** "You can trust a damaged index if the damage would not affect your lookup."
  - `/sw/*/lib/libz.so.1` depends only on `/sw` and each package's `lib/`; damage under `share/` or `bin/` is irrelevant.
  - A first match is invalidated only by damage in candidates at or before the hit in byte order. A full expansion or a negative result depends on every candidate.
  - Repair is lazy and targeted: a lookup repairs only the damage it overlaps, as demand-driven incremental systems such as Salsa and Bazel do. Stamps are per directory, so a damaged candidate directory is re-read, which is cheap; rebuilding must stay cheap for this to work.
  - Per-directory granularity suits Fluffy's packaging model. Package directories are small, apart from the large header trees (linux-headers, glibc's `include`). And since packages are read-only squashfs images, nothing below `/sw/<pkg>` changes except by mounting a different image: in practice damage only lands on `/sw` and on package mount points, never partway into a package.
- **Prior art.**
  - Plan 9's union directories (`bind -a`): an ordered search built into the namespace, close to what `/sw/*` does with glob. Linux never adopted them; overlayfs is the nearest relative, with the depth limits noted above.
  - btrfs's per-node generations (`find-new`): ordered by inode, not path, and blind to squashfs mounts.
  - macOS FSEvents: "changed under this directory since event N", built on a log.
  - io_uring could batch validation `statx` calls for long-running programs, but ring setup costs more than it saves for the thousands of short-lived processes a build spawns.

### Idea: faster locales in glibc's INSTALL (2026-11-20)

- **Why it is slow:** glibc's recipe runs `make localedata/install-locales`, which builds all 502 locales in `localedata/SUPPORTED` with `localedef`, one after another (each adds to one shared `locale-archive`, and the log shows them completing in order despite `-j`). Each compile starts from scratch, and most of the work is two big categories that most locales share: `LC_COLLATE` (nearly all `copy "iso14651_t1"`: tens of thousands of collating elements with several levels of weights, built by the slow `ld-collate.c`) and `LC_CTYPE` (`copy "i18n"`: character classes over all of Unicode). The archive deduplicates identical tables afterwards, by hash, but the CPU has already been spent.
- **Counts (2026-11-20, glibc 2.44, resolving `copy` chains to the locale whose own text defines the category):** `LC_COLLATE` has 144 distinct compiles of (source, charmap) instead of 502, the largest group `iso14651_t1` under UTF-8 shared by 197 locales (then ISO-8859-1 by 43, `es_ES` UTF-8 by 30); `LC_CTYPE` has 233 instead of 502 (`en_US` UTF-8 by 36, `es_ES` UTF-8 by 27, `ar_EG` UTF-8 by 19). Counting a category as shared only when its body is exactly one `copy` line; near-copies (a copy plus a transliteration include) still count as distinct. The saving in time should exceed the counts: the most expensive compile, `iso14651_t1` under UTF-8, would run once instead of 197 times, while 8-bit charmaps' compiles are cheap. Not yet timed: a few `localedef` runs would make it a measurement.
- **Approach A (in the build, no glibc patch):** a compiled locale is a directory of per-category files, each depending only on its category's resolved source and the charmap. Group locales by that; compile each group once, as separate files (`localedef` without the archive, as `install-locale-files` does); for the rest compile only their own categories and link in the shared `LC_COLLATE`/`LC_CTYPE`; then `localedef --add-to-archive` the directories into the usual `locale-archive`. Separate files also let the compiles run in parallel. Proof: build both ways and compare every category file and the archive, byte for byte.
- **Approach B (upstream):** a `localedef --cache-dir`, keyed by the hash of a category's resolved text (every `copy` followed), the charmap and `localedef`'s version, emitting cached bytes on a hit. It also catches near-copies, but patches the core of `localedef`, and collation's use of character-set information must be in the key.
- **Other options:** build fewer (LFS offers a short `localedef` list or `install-locales`; Fluffy uses the latter), `install-locale-files` with `-j` alone (same work, less wall time), `C.UTF-8` (built in since glibc 2.35) where it suffices, or locales as their own packages found through `/sw/*/lib/locale`.
- **Leaning (user):** A.

### The swctl split, then swctl packages (decided 2026-11-20, not started)

- **The problem:** ON does two jobs. It says where a build runs (on the host for `host-build`, or in a Fluffy chroot) and which tools swctl itself uses to fetch, unpack and package (`cross-build`'s pass1 set or `fluffy-build`'s final set), and the toolset is mounted into every build's `/sw` beside BUILD_NEEDS. So builds see tools they never declared: zstd found zlib and xz from `cross-build` (Chapter 8 notes), and binutils' and glibc's CROSS lists have no binutils, which only works because something else supplies it. Every recipe's checksum also includes the ON target's image, so changing a toolset package (`curl-pass1`, `git-pass1`) rebuilds nearly all of world. CROSS repeats the same stage decision a second time, in each recipe's two BUILD_NEEDS lists.
- **Step 1, the split:** `lockdown_exec` mounts only BUILD_NEEDS for MAKE, CHECK and INSTALL, so each build sees exactly what it declares. PREPARE and SQUASHFS stay as they are: they are swctl's own work, and keep its toolset. swctl's own process keeps running across the change of view (its bash is loaded, its calls go through ctypes.sh). Every recipe that silently relied on the toolset then fails with a clear "not found", fixed by adding the tool to its BUILD_NEEDS; a static check (each phase's commands against its BUILD_NEEDS) could find most before a world run.
- **Step 2, swctl packages:** `swctl-pass1` and `swctl` take over what `cross-build` and `fluffy-build` do today, also installing swctl itself (signing and download checks belong with it later, see "Signing removed"). The swctl package's image need no longer key builds: a source is pinned by its commit whichever git fetched it. Only SQUASHFS's output depends on swctl's tools (mksquashfs's version shapes image bytes), so that is keyed separately, or packaging is made reproducible across versions.
- **Then:** ON goes, and what host-build means is redesigned around the packages (a recipe property: built on the host). How BUILD_NEEDS names stage variants (today two lists under `test -v CROSS`) is decided after step 1 shows what builds really need. Considered and set aside for now: automatic provider resolution ("latest provider without a cycle" reorders world away from LFS; "most recent provider in the book's order" needs an explicit ordered list), and a bracket convention (`'gcc[-pass2]'`: the variant under CROSS), which converts 91 of 95 recipes mechanically; the four exceptions were linux-headers (host-build under CROSS), binutils and glibc (no binutils under CROSS), and autoconf (automake natively only).

### Signing removed (2026-11-20)

- **Decision (user):** swctl no longer signs or verifies `/sw/.build/fstab`. Signing will come back only with apt-get-like operations: a download check on a fetched fstab, blessing a published set of images (the remote-manifest design in "The Manifest & System Installer Architecture" above). Until then it was ceremony: only root or the build user can change the local fstab, nothing at boot checked the signature, and integrity is already content-addressed (each line's `X-fluffy.image-checksum`).
- **Removed:** `sign_file`, `verify_fstab_signature` and the check on every fstab load; `sign_and_save_fstab` became `save_fstab` (no `# fluffy.signature=` header; an old header is dropped on the next save, since libmount keeps it as the intro comment); `signify-pass1` from `cross-build` and `signify` from `fluffy-build` (the builder environments). signify stays a package for publishing and download checks, now a final `sw/signify` in world; it needs no pass1, since nothing is published during a cross build; `fix-fstab`, a one-shot migration that ended by re-signing. The keys under `/sw/.build` (`sign.sec`, `sign.pub`) are unused and can be deleted by hand.
- **Effect:** one package less on the bootstrap path, no signing key on CI or spot machines, and the parallel world's fstab merge needs no key.
- **Later (user):** swctl will probably need its own package, like any other tool Fluffy installs, rather than living only in the repo; signing and download checks would come with it.

### CI hosting (2026-11-20, open)

- **Goal:** get CI off the user's PC, for hermeticity and security, cheaply, and ideally under a *true hard* spending limit (spending can't exceed it, not just alerts). Today a Buildkite agent (`buildkite-agent` user) runs `swctl build world` on the same machine (`.buildkite/pipeline.yml`, 720-minute timeout); its persistent `work/` (archives, `work/git`) and previous squashfs images are what keep incremental worlds fast.
- **GitHub-hosted runners:** Actions can run a Buildkite agent, and Fluffy's mechanics work there (passwordless sudo, user/mount namespaces, chroots, squashfs; the Ubuntu 24.04 kernel is new enough for per-namespace `binfmt_misc`). But a job runs at most 6 hours, every run starts on an empty machine (Actions' cache is about 10 GB per repository), and standard runners have 4 cores and about 14 GB free disk: a cold world doesn't fit. Viable only with a binary cache (below) or by splitting world into stages passed on as artifacts.
- **Options, cheapest first:**
  1. *A VM on the PC* (KVM): free; CI can no longer see the user's home, keys or processes; caches on the VM's disk keep builds fast; a clean snapshot resets it. Not off the PC's hardware.
  2. *Flat-rate machine* (rented dedicated server, or Hetzner Cloud, whose hourly billing stops at the monthly price): the fixed price is a hard limit by construction. Hetzner raised prices sharply in 2026 (CCX dedicated-vCPU plans roughly +113–173% for new orders from 15 June); a CCX43 (16 dedicated vCPU, 64 GB, 360 GB) was about €0.44/hour, €276/month in the EU in November 2026 (Helsinki reportedly ~15% cheaper since 10 November).
  3. *Spot/on-demand cloud VMs*, started per build with a persistent volume for the caches, deleted after (`buildkite-agent --disconnect-after-job`). Spot: AWS EC2 Spot (Buildkite's Elastic CI Stack autoscales it), Google Cloud Spot VMs (no fixed max runtime), Azure Spot VMs, Oracle preemptible (its free ARM tier doesn't fit x86_64 Fluffy). Hourly, no pre-emption: Hetzner Cloud, DigitalOcean, Vultr, Akamai/Linode, Scaleway. Outside AWS, starting machines per build needs a small script or webhook. A pre-empted world resumes rather than restarts, thanks to per-package images.
  4. *$0:* free GitHub runners plus a binary cache (below).
- **Hard spending limits:** Azure's real spending limit exists only on credit-based subscriptions (free trial, Visual Studio subscription credits, Azure for Students): resources stop when the credit runs out. Pay-as-you-go Azure, AWS and GCP only have budgets that alert or trigger automation (soft caps); GCP's "disable billing for the project" pattern is near-hard (minutes to hours of lag, and it stops everything, the cache disk included). A flat-rate machine is the other true limit.
- **Price comparison, November 2026 (aggregator figures; check the providers' own pages):** Azure Spot D16as v5 (16 vCPU, 64 GB, Linux, East US) about $0.145/hour (on-demand about $0.69), so roughly $106 for a month always on, plus managed disk, IP and egress, with eviction risk; Hetzner CCX43 about €0.44/hour as above. Per 6-hour world: roughly $0.90 against €2.65. A Visual Studio Professional subscription's monthly Azure credit (around $50) would buy about 340 such spot hours under a cap that can't be exceeded, the cache's managed disk billing against it too.
- **Leaning (user):** Azure, for the true hard limit (credit-based subscription, spot VMs, persistent cache disk). Nothing set up yet.
- **Idea: a binary cache.** Fluffy's images are deterministic, checksummed in the fstab, and keyed by their recipes. If swctl could download an image whose recipe (and includes, inputs) hasn't changed, from GitHub releases for example, instead of building it, most runs would only build what changed. That makes free 6-hour runners viable, speeds up any fresh machine, and helps every Fluffy user, not just CI. A sizeable design: what exactly keys an image, who signs and publishes, and how a client trusts a downloaded image (the fstab manifest's signature already covers what's installed).

- **Idea: a parallel world on Buildkite (2026-11-20).** World is a DAG and the planner already computes it.
  - *Shape:* a first step runs the planner and uploads a generated pipeline (`buildkite-agent pipeline upload`), one step per package with `depends_on` edges from NEEDS and BUILD_NEEDS. On-demand spot machines pick steps up as their dependencies finish (`--disconnect-after-job`), so independent packages build side by side.
  - *Images between steps:* each step downloads the images of its BUILD_NEEDS closure. Stored by content hash, that storage is also the binary cache above: a step whose recipe, includes and inputs are unchanged finds its image and finishes in seconds, across runs as well as within one. (A pipeline is fixed once uploaded, so the DAG can't prune itself mid-run; quick cache-hit steps come to the same thing.)
  - *fstab through the DAG:* each step passes on its input fstab with its own package's line added. Every package is built exactly once, so branches only add disjoint lines, plus identical copies of shared ancestors' lines. At a join (many to one), the step takes the union of its parents' fstabs: identical lines collapse; two different lines for one package are an error (a bug); lines are written in the planner's order, so the merged file is the same whichever branch finished first.
  - *Signing:* not an issue any more: local signing was removed (2026-11-20, "Signing removed"), so a join just takes the union of its parents' fstab lines, and each step checks its input images by their `X-fluffy.image-checksum`. Signing returns only when a finished set is published for download.
  - *Limits:* the critical path (binutils → gcc → glibc → the final toolchain, with glibc's and gcc's long test suites) bounds the wall-clock time, and packages already use every core (`make -j$(nproc)`), so the gain comes from serial phases (configure, single-threaded tests) and the many small packages. Total compute stays about the same, plus per-step overhead: machine start-up, image downloads, and preparing Fluffy's base root (what `bootstrap.sh` makes) before the chroot; very small packages may be worth grouping along a chain.
  - *Brainstorm, 2026-11-20 (user):*
    - *The pipeline:* the generator writes one step per package, `key: <pkg>`, with `depends_on` the keys of its ON target and BUILD_NEEDS; about 134 steps fits a pipeline upload. Buildkite's automatic retry on a lost agent (`retry: automatic` for the agent-lost exit status) reruns a step whose spot machine was evicted.
    - *No single-package command:* a step's machine has its dependencies' images and fstab lines, so plain `swctl build <pkg>` walks the closure as usual; every dependency validates instantly (recipe checksum matches, image present) and only `<pkg>` builds. Cheap validation is what makes the existing command enough.
    - *Downstream sees upstream changes for free:* `X-fluffy.recipe-checksum` covers the recipe, its includes and the image checksums of its direct dependencies, so a changed upstream image changes every downstream key, and a byte-identical one changes none: early cutoff works across machines. The missing piece is storage: a blob store keyed by image checksum (an Azure Storage container beside the spot VMs, say), from which each step downloads its closure's images, plus the merged fstab passed down the DAG. Kept between runs, it is the binary cache.
    - *Builder size per recipe:* a recipe variable such as `BUILDER=large`, read by the pipeline generator (not exported by swctl, so the knobs rule holds), maps to a Buildkite queue (`small`, `medium`, `large`) backed by a spot VM size. Small configure-bound packages gain little from more cores; gcc, glibc and linux scale well and dominate the critical path, so big machines pay off there. With per-package timings (the planned `/sw/.build/timings`), the generator could pick sizes from recorded build time and core scaling, the recipe value only overriding it.
    - *A prebaked VM image:* the host tools (now including autoconf, automake and libtool), the Buildkite agent and Fluffy's base root baked into the spot machines' image, so a step starts with a disk attach and some downloads instead of setup; that matters most for small packages.
  - *`swctl buildkite` (2026-11-20, user; first cut done 2026-11-20):* first cut runs on the single local agent, steps one at a time through a concurrency group per FLUFFY root (they share its /sw and fstab), no image store yet; a step's `depends_on` is its BUILD_NEEDS (ON included) and, transitively, what those NEEDS, never its own NEEDS. Original idea: the planner's DAG emitted straight as a Buildkite pipeline. `.buildkite/pipeline.yml` shrinks to one step, `./swctl buildkite world | buildkite-agent pipeline upload`, and the generated steps are one per package: `key: <pkg>`, `command: ./swctl build <pkg>` (its dependencies validate instantly, so only `<pkg>` builds), `depends_on` its ON target and BUILD_NEEDS, `agents: { queue: <size> }` from the builder size, and automatic retry on a lost agent (spot eviction). swctl gains the CI-specific code itself, deliberately: no generic `swctl plan --json` plus converter, since an abstraction with one consumer only ends up defining that consumer's shape. A second CI would get its own command when it exists.
    - *fstab lines as Buildkite meta-data:* each step publishes its package's line (`buildkite-agent meta-data set fstab/<pkg> "<line>"`), and a step assembles exactly the fstab its closure needs (`meta-data get` for each key, written in planner order). No fstab files passed along the DAG and no merge at joins; images still come from a store keyed by image checksum (the binary cache).
    - *Images in Azure Blob storage (decided 2026-11-20, user):* not Buildkite's own caching. Its cache volumes exist only on Buildkite-hosted agents; Buildkite Cache (`buildkite-agent cache save`/`restore`) works on self-hosted agents but only with an S3 or S3-compatible store and AWS credentials (Blob doesn't speak S3), and its entries expire three days after creation or last restore, too short for images a world fstab depends on. Instead, one Blob container: `images/<image-checksum>.squashfs` (written once, never overwritten) and `recipes/<recipe-checksum>` (the fstab line that recipe produced). A step looks up its recipe checksum; on a hit it downloads the image and skips the build, otherwise it builds and uploads both. The spot agents authenticate with a managed identity (no keys on the machines), and storage bills against the same capped subscription. A per-VM local copy keyed by image checksum can sit in front of it if downloads are slow (images never change, so it never goes stale). `swctl buildkite` does this with `azcopy` or `curl`, no plugin.
    - *Caches inside `.git` (2026-11-20, user; after the first DAG run):* the agent's default checkout cleaning (`git clean -ffxdq`) deletes the gitignored `work/` before every step, so each step refetches its own package's sources (no worse than today's single world step, which starts from an empty `work/` every build). Moving the long-lived caches, the bare store `work/git` and `work/archives`, to `.git/fluffy/git` and `.git/fluffy/archives` keeps them: `git clean` and Buildkite's checkout never touch `.git`, and git (`gc`, `fsck`) ignores directories it doesn't know. The checkout is bind-mounted into the chroot at its own path, so swctl reaches them as it reaches `work/`. Find the directory with `git rev-parse --git-common-dir`, so worktrees (where `.git` is a file) share one cache. Scratch (`src`, `installed`, test results, `phase.log`) stays in `work/`. The quick alternative is `BUILDKITE_GIT_CLEAN_FLAGS: "-ffdq"` in the pipeline's env (the default without `-x`).
    - *No static pruning:* the generator can't know which packages will be unchanged (a recipe's key includes its dependencies' image checksums, known only once they're built), so it emits every step, and an unchanged one finishes in seconds as a cache hit.
  - *First measure:* per-package durations from one complete world log (the log prints each phase's time, e.g. `curl [113/134]: PREPARE(0s) MAKE(1m9s)…`); the critical path against the total gives the best possible speedup, before designing anything.
- **Idea: a Fluffy VM on Azure that does our builds (2026-11-20, user; far off).** Fluffy building Fluffy: the CI machine runs what it builds, cross builds included. Needs, in order: a green cross world, then fluffy-build (non-cross) plans, then a cross build whose host-build recipes are satisfied by Fluffy's own host tools. The image: Azure boots a custom image uploaded as a fixed-size VHD; the kernel needs the Hyper-V drivers (`hv_vmbus`, `hv_storvsc`, `hv_netvsc`), and the VM must report ready to Azure, through a provisioning agent (`waagent`, cloud-init) or a small step of our own, or Azure marks it failed. With the parallel world, each spot VM boots the Fluffy image, mounts images from the Blob store, runs one step and exits; the prebaked VM image above becomes a Fluffy image.

### `pkgconf` (decided 2026-11-17, done 2026-11-18)

This reversed the earlier "`pkg-config` is verboten" decision. `pkgconf` is back, exactly as LFS 13.1 builds it, and Fluffy's home-grown replacement is gone.

- **What went away:**
  - `HAS_CFLAGS=`/`HAS_LDFLAGS=` in recipes, the `X-fluffy.cflags`/`X-fluffy.ldflags` fstab options, and `swctl`'s `<DEP>_CFLAGS`/`<DEP>_LDFLAGS`/`<DEP>_LIBS` exports.
  - Meson's `SystemLibraryDependency` (`dependencies/base.py`, `detect.py`, `modules/pkgconfig.py` and its unit test), and the dependency renames it forced in kmod's and systemd's `meson.build`.
  - Every `PKG_CONFIG="false"` and hand-written `<NAME>_CFLAGS`/`<NAME>_LIBS` in recipes, and the patch hunks that let configure run without `pkg-config`: the "pkg-config not found" errors removed from btrfs-progs, e2fsprogs, elfutils, kbd, p11-kit, procps-ng and shadow, the `-lfoo` link probes in iproute2, and the `<NAME>_CFLAGS` aliases in btrfs-progs, elfutils, grep and kbd.
  - The multi-library package-splitting rule. With `.pc` files, a project such as glib can be one package again.
- **What `pkgconf` learned** (`fluffy/pkgconf-3.0.5` in `../pkgconf`, two commits; tests in `t/fluffy/`):
  - Each search-list element goes through `glob (element, GLOB_PATHS | GLOB_NOMAGIC)`: a whole `*` component expands in byte order, as for `execvp`, and any other element is kept as it is. No fallback for other C libraries: pkgconf and pkgconf-pass1 both link Fluffy's glibc. The default list comes from the build: `with-pkg-config-dir='/sw/*/lib/pkgconfig:/sw/*/share/pkgconfig'`, `lib` before `share` as upstream orders them. `PKG_CONFIG_PATH` and `PKG_CONFIG_LIBDIR` take the same patterns.
  - **"Zero `-I`/`-L`" stays true.** `with-system-libdir='/sw/*/lib'` and `with-system-includedir='/sw/*/include'` go through the same expansion, so `-I/sw/zstd/include` and `-L/sw/zstd/lib` are stripped like `-I/usr/include`, and output is just `-lzstd` plus any truly extra flags. A subdirectory such as `-I/sw/util-linux/include/libmount` is kept.
- **Recipes.**
  - `sw/pkgconf`: LFS 8.21. Meson from `meson.py` in the meson tarball, `ninja test`, and `pkg-config`/`pkg-config.1` symlinks. No versioned doc directory.
  - `sw/pkgconf-pass1`: not in LFS, whose chapter 6 builds nothing that needs `pkg-config`; Fluffy's does (curl-pass1, util-linux-pass1, ctypes-sh-pass1, python-pass1). Autotools, `host-build`, the same search path, so it searches the `/sw` being built and never the host's. Its system directories are the ones stock gcc-pass1 searches (`/sw/glibc/include:/sw/linux-headers/include`, `/sw/glibc/lib`), so it prints every other package's `-I`/`-L` in full.
  - **Order follows LFS: ninja (8.20), pkgconf (8.21), then binutils (8.22).** In the cross stage `ninja` and `pkgconf` build with the chapter 6 and 7 tools (`bash-pass1`, `binutils-pass2`, `gcc-pass2`, `python-pass1`, `sed-pass1`, `util-linux-pass1`); every final package after them may use `pkgconf`. `ninja` runs on `bash-pass1` and links `libstdcpp-pass1` (`NEEDS`), as LFS's ninja runs on whatever `/usr` holds; the final `bash` and `libstdcpp` mount over them once built, as with systemd's `util-linux-pass1`. **Open:** this breaks the rule that a final package's `NEEDS` names no `-pass` package (see "Runtime `NEEDS=(...)` is Strictly Invariant"), as systemd's `util-linux-pass1` already did. Either the rule gains this exception, or the cross stage's consumers take `pkgconf-pass1` and the final `pkgconf` moves after `bash` and `libstdcpp`, which departs from LFS order.
  - **`BUILD_NEEDS` lists `pkgconf` only where upstream calls `pkg-config`:** binutils, btrfs-progs, curl, dbus, e2fsprogs, grep, iproute2, kbd, kmod, libelf, man-db, p11-kit, procps-ng, python, shadow, systemd, util-linux, zstd; `pkgconf-pass1` in ctypes-sh-pass1, curl-pass1, python-pass1, util-linux-pass1.
  - `.pc` files as LFS installs them: ncurses `--enable-pc-files --with-pkg-config-libdir=/sw/ncurses/lib/pkgconfig` and the `${lib}.pc` → `${lib}w.pc` links (an explicit libdir needs no `pkg-config` at configure time); libelf `config/libelf.pc` by hand.
- **Install directories from other packages' `.pc` files.** `systemd.pc`'s `systemdsystemunitdir` and `udev.pc`'s `udevdir` name `/sw/systemd/...`. A consumer must never install there: dbus, e2fsprogs, man-db and util-linux pass their own unit directories, and btrfs-progs' patch keeps `UDEVDIR='${prefix}/lib/udev'`. Check every new recipe that has both `pkgconf` and `systemd` in `BUILD_NEEDS`.
- **Not yet checked:** how `PKG_CONFIG_SYSROOT_DIR` interacts with wildcard system dirs. Nothing uses it today.

### Working Rules

- **Patches are generated from git (started 2026-11-18; readline converted first).** Each package's changes are real commits on `fluffy/<upstream-tag>` in its repository one level up (`../<pkg>`). The recipe applies one file, `sw/<pkg>-<ver>-fluffy.patch`, generated from them with stock git.
  - **Base.** The first commit on the branch makes the tree exactly the release tarball the recipe downloads (upstream tags often differ: coreutils by about 2,400 generated files), and is tagged `fluffy-base/<upstream-tag>`. It is not part of the series. For glibc the tag equals the tarball.
  - **Generating.** Stock git, from the package repository: `git format-patch --stdout --no-signature --no-renames fluffy-base/<tag>..fluffy/<tag> > ../fluffy/sw/<pkg>-<ver>-fluffy.patch`. The file is an mbox: `git am` rebuilds the commits from it, and GNU `patch` skips the messages. `--no-signature` keeps git's version out of the file; `--no-renames` keeps renames as delete-and-add, which `patch` can apply. Binary files cannot go in (`patch` cannot apply them), and a commit message must not quote a diff, which `patch` would apply too; `series-equiv` catches both.
  - **Applying.** Recipes call `apply_patch <file>` (a swctl function), not `patch` directly. Git diffs carry no timestamps and GNU `patch` has no option to keep a file's mtime, so `apply_patch` runs `patch -Np1` and then gives every file that already existed its old mtime back. Otherwise a patched `configure.ac` could look newer than `configure` and make would rerun autoconf. New files keep the time of patching.
  - **Proving a conversion.** `tools/series-equiv <tarball> <old1.patch>:<old2.patch>... <new.patch>` applies the old patches as the old recipe did (`patch -Z`) and the new one through `apply_patch`, with swctl's umask, and compares contents, types, modes, and tarball files' mtimes (new files' mtimes are only noted). Run it before deleting the old patches.
  - **History.** Interactive-rebase the branches freely until release, then regenerate. Upstream fixes are their own commits with the upstream author and commit named in the message.

- **Archives (decided 2026-11-18).** swctl unpacks `ARCHIVES[0]` (if it is a tarball) and changes into it. `ARCHIVES[1…N]` are placed one level up, beside that directory and never unpacked, and the recipe uses them from there, as LFS does:
  ```
  tar -xf ../mpfr-$MPFR_VERSION.tar.xz
  mv -v mpfr-$MPFR_VERSION mpfr
  apply_patch ../gcc-$VERSION-fluffy.patch
  ```
  An earlier build script had swctl unpack every tarball into the first archive's directory. All recipes were moved to this layout on 2026-11-18: gcc-pass1, gcc-pass2 and pkgconf unpack their extra tarballs themselves; glibc, python, systemd and tcl unpack their data and docs tarballs at install time, LFS-style. python's HTML docs were silently never installed under the old layout.

- **Build priority is nice 9 with the idle I/O class (2026-11-18).** That is the lowest the test suites allow:
  - nice 19 fails glibc's `posix/tst-nice` (`nice(10)` must raise the value by 10);
  - `SCHED_IDLE` and `SCHED_BATCH` fail `tst-sched_setattr` and `tst-sched_setattr-thread`, which require `SCHED_OTHER`.
  - *Planned:* set the policy per phase, a rule for every package rather than a recipe knob. MAKE and INSTALL are throughput work that no test observes, so they run under `SCHED_IDLE` and take only spare CPU. CHECK stays under `SCHED_OTHER` at nice 9, which the test suites expect. Each phase already runs in its own sandbox, set up as root, so `lockdown_exec` sets the policy there before dropping privileges, and the phase's process tree inherits it.
  - *Not yet tried:* a cgroup with `CPUWeight=1` and `IOWeight=1` (for example via `systemd-run --scope`), which yields as strongly while processes still see nice and `SCHED_OTHER`.
  - Don't stop a build with Ctrl-Z during tests: their timeouts are wall-clock, so stopped compiles fail as timeouts.

- **Idea: time left in the progress line (2026-11-18).** The question is "how long does this have left?" at a glance. The only change is an `XhYm left` after the current/total count:
  ```
  glibc [41/132 3h12m left]: PREPARE(3s) MAKE(2m34s) CHECK(18m51s) INSTALL(2m8s) PACKAGE(11s)
  ```
  - It is the expected duration of this run (the recorded durations of every package it builds, skipping those that will be `UP-TO-DATE`) minus the time elapsed since the run started. Once elapsed time passes the expectation it reads `XhYm overtime` instead. It updates once per package; the line stays append-only.
  - Without a recorded duration for every package the run builds, it shows nothing; a partial guess would mislead.
  - Durations live in a local, display-only file such as `/sw/.build/timings`, rewritten after each build. Never put them in the fstab or the images: they differ by machine and run, so every rebuild would change the manifest even when every image is identical.

- **Planned: phases without a controlling terminal (2026-11-18).** Anything a phase writes to `/dev/tty` bypasses `phase.log` and lands in the middle of swctl's progress line, for example `CHECKvia send_tty(13s)` from expect's `tests/logfile.test`. glibc writes its fatal errors there too. That is likely why the `mksquashfs` crash showed only "Aborted (core dumped)" and its reason was never seen. (That crash came from gcc-pass1's specs file dropping `--eh-frame-hdr`; see the libgcc-pass1 CHECK.)
  - Fix: swctl runs each phase in a new session (`setsid`), so no phase has a controlling terminal. `/dev/tty` is then unavailable inside builds, and such output goes to stderr, which is the phase log.
  - expect is not a blocker: `logfile.test` calls `send_tty` only when `::tty_spawn_id` exists, and its expected log matches either way. Other test suites may behave differently without a terminal (skip, or fail), so validate with a full world, not package by package.

- **swctl exports only build-environment knobs (decided 2026-11-18).** Variables such as `DESTDIR`, `FLUFFY` and `CROSS` describe the build environment and belong in swctl. Anything that names a package's path or tunes one package belongs in that package's recipe or patch. A variable that only works around a package bug, such as the former `GCC_EXEC_PREFIX=/sw/gcc/lib/gcc/`, is fixed in the package instead.

- **Nothing linked against the build host's C library gets Fluffy's glob patches (decided 2026-11-18).** gcc-pass1 is the one such compiler: stock gcc plus LFS's own edits, with absolute paths where the other gccs search `/sw/*` (`STARTFILE_PREFIX_SPEC "/sw/glibc/lib/"`, `--with-as`/`--with-ld` into `/sw/binutils`, `--with-gxx-include-dir=/sw/libstdcpp/include/c++`, and a specs file adding `-idirafter /sw/glibc/include -idirafter /sw/linux-headers/include`). The pass1 packages it compiles take another package's headers by absolute `-I` (bash-pass1 and util-linux-pass1: `/sw/ncurses/include`; squashfs-tools-pass1: `/sw/zstd/include`) or from pkgconf-pass1. Everything else links Fluffy's glibc, so its patches use `GLOB_PATHS` unconditionally, with no `#ifdef` fallback. binutils-pass1 is the other host-linked package still carrying glob code (standard `glob()` only); it is next.

- **Shell style.**
  - No semicolons except `;;` in `case`.
  - Lean on `set -e` and `trap ERR`, not `$?` checks.
  - Use subshells, not self-invocation.
  - Use `call mount`, not the `mount` command; use libmount, not `grep`.
  - Never change `swctl`'s shebang (it breaks the chroot).
- **`swctl` scope.** Keep it under ~1k LOC with one reusable DFS. Key generation is not part of `swctl`. Logic that is "too magic" does not belong in it. It never pulls from the packages directory.
- **Patches.**
  - Generated, then reviewed by hand ("auto generate, manual review"), and kept for reviewability.
  - Split into `-shell`, `-source`, and `-test`.
  - Never change file times (`patch -Z`).
  - Fix problems at the proper place rather than disabling tests ("we should fix glibc").
  - Any patched behavior gets a test, and `CHECK()` runs wherever possible.
  - Custom flags go at the high end of the bit range.
- **Versionless doc directories (decided 2026-11-17; cleanup pending).**
  - Docs go in `/sw/<pkg>/share/doc/<pkg>`, never `/sw/<pkg>/share/doc/<pkg>-$VERSION`. Only one version of a package is installed at a time, and `/sw/<pkg>` already namespaces it, so the version suffix (inherited from LFS's shared `/usr/share/doc`) adds nothing. It also breaks links and paths from other packages on every upgrade.
  - Autoconf's default `docdir` (`${datarootdir}/doc/${PACKAGE_TARNAME}`) is already versionless, so in most recipes the fix is to delete the `--docdir=` line.
  - Recipes to convert, as of 2026-11-17:
    - `--docdir=…-$VERSION`: `acl`, `attr`, `automake`, `bash`, `bison`, `bison-pass1`, `flex`, `expat`, `gettext`, `gmp`, `gperf`, `man-db`, `mpc`, `mpdecimal`, `mpdecimal-pass1`, `mpfr`, `pcre2`, `procps-ng`, `readline`, `sed`, `util-linux`, `xz`, `xz-pass1`.
    - `-Ddocdir=…-$VERSION`: `systemd`.
    - Hand-made `share/doc/<pkg>-$VERSION` in `INSTALL()`: `curl`, `dejagnu`, `expat`, `gawk`, `ncurses`, `python`, `readline`, `sed`, `tcl`.
    - `vim`'s `share/doc/vim-$VERSION` symlink.
    - `openssl`'s `mv share/doc/openssl share/doc/openssl-$VERSION`: drop the `mv` and keep upstream's name.
  - Find any stragglers with `grep -n 'share/doc[^ ]*\$VERSION' sw/*`.
- **No backward compatibility while developing**, including migration logic ("that's just backwards compat under a different name"). No `sbin`, and no `/bin/sh` symlink.
- **Agents never run `sudo`.** Hand the user `sudo --preserve-env=FLUFFY,CROSS ./swctl build <pkg>` (always both: `CROSS` must pass through even when unset).
- **Resources.** The build host is 16 GB / 8 cores, and builds run at low priority.

### Recurring Build Pitfalls

- **Deleting a source file from a glibc build tree is not enough.** The object stays in the subdirectory's `stamp.o*` lists and, worse, in `libc_pic.a` and `libc.a`: `ar` adds and updates members but never removes them, so `libc.so` keeps linking the deleted code. After deleting a source, remove its objects, the subdirectory's `stamp.o*`, and `libc.a`/`libc_pic.a`/`libc_pic.os`/`libc.so`, then rebuild; verify with `nm`. (Found 2026-11-17: v5's `fswc.c` survived its deletion this way.)
- **Restoring a file with `cp -p` or `mv` of a `cp -p` copy keeps its old mtime,** so `make` does not rebuild and you test the previous build. `touch` it after restoring.
- **A test prefix must look like the real one.** v6 passed every local test and then failed four in `world`, because the real `/sw` holds an image file beside each package directory and the test tree held only directories. The FSWC oracle now builds its prefixes after `/sw` (image files, symlinks, odd names, thousands of entries). A local run that binds the extracted packages into a private `/sw`, with an empty `.squashfs` file beside each, reproduces three of the four (`tst-glob-bz30635` needs real SquashFS). Found 2026-11-17.
- **`libc_malloc_debug.so` with `MALLOC_CHECK_=3` is not fork-safe in threaded programs.** Its checker has its own copy of `main_arena`, whose lock `fork` does not reset, so a child forked while another thread allocates can block forever in `malloc_check`. Use it in single-threaded test workers only. Found 2026-11-17 while chasing what looked like an FSWC deadlock.
- **A bare `gcc` could not find `cc1`** ("cannot execute 'cc1': posix_spawnp: No such file or directory"), fixed 2026-11-18. The driver locates its own directory from `argv[0]`, and for a bare name libiberty's `make_relative_prefix` split `PATH` on `:` with no wildcard support, so `/sw/*/bin/gcc` never matched and the driver fell back to relative `../libexec` paths. swctl hid it by exporting `GCC_EXEC_PREFIX=/sw/gcc/lib/gcc/`. Now `gcc.cc` resolves a bare `argv[0]` with `glob ("{" PATH "}/" NAME, GLOB_PATHS)`, as `execvp` found it, before calling the stock `make_relative_prefix`, and the export is gone. The fix lives in `gcc.cc`, not libiberty, because libiberty is also compiled for the build machine inside gcc-pass2's build, against the host's C library. `gcc.dg/fluffy/fluffy.exp` runs `xgcc` by a bare name through a `<objdir>/*` `PATH` element with `GCC_EXEC_PREFIX` unset.

- `/bin/sh: bad interpreter`. Fixed per package with `-shell.patch` files from `mkbashpatch`, then hand-reviewed.
- Wildcard configure values expanded by the build shell. Always single-quote them (`--with-lib-path='=/sw/*/lib'`).
- `libgcc_s.so.1`. `mksquashfs` needs it for `pthread_exit`, hence the separate `libgcc` package. Cross-built `libstdc++.so` from the `--disable-shared` `gcc-pass1` driver lacked `DT_NEEDED libgcc_s.so.1` until a `-shared`-only specs file was added to `sw/libstdcpp-pass1` and `sw/gcc-pass2`.
- `glibc-pass1` builds with `-Werror` and `glibc` does not, so warnings break only pass1.
- `SOURCE_DATE_EPOCH=0` gives every package root mtime 0. Never use mtime as identity.
- **Test-harness traps found while moving `CHECK()` tests into test patches (2026-11-16):**
  - **`set -e` is off inside `( … ) && …`.** Bash disables errexit inside any `&&`/`||` list. A phase runner written that way ignores a failure in the middle of `MAKE()`/`CHECK()`, and only the last command counts. `swctl`'s `run_phase` is not affected.
  - **util-linux `tests/run.sh --nonroot` run as root** prints "Ignore util-linux test suite" and exits 0, a silent pass.
  - **GNU `patch` cannot set the exec bit from a `-Naur` diff.** New executable test files need git-style `new file mode 100755` hunks. Patch 2.7.6+ honors them inside an otherwise `-Naur` patch.
  - **A user namespace that maps one uid/gid** fails gnulib's `test-chown`/`test-fchownat`/`test-lchown`, which is expected outside `swctl`.
- **Local verification without `swctl`:**
  - Unsquash the newest final images into a scratch directory and bind them at `/sw` inside `unshare -Urm`.
  - Then drop to your own uid with a nested `unshare -U --map-user`, and run a recipe's phases with a scrubbed environment.
  - This needs `kernel.apparmor_restrict_unprivileged_userns=0` on Ubuntu 24.04.
  - Installed images may predate the current patches, so always rebuild.

- **`libstdcpp` Standalone Build & POSIX Gthreads Support**:
  - When `libstdc++-v3` is configured standalone outside of the full GCC build tree, its configure script checks for gthreads by compiling `#include "gthr.h"`.
  - `gthr.h` includes `"gthr-default.h"`, which is normally generated as a symlink during `libgcc` builds. - **Autosetup `$CROSS` Collision Note**:
  - `autosetup` (used by modern SQLite and other tools) defines its cross-compilation prefix directly from the `CROSS` environment variable: `define cross [get-env CROSS $cross]`.
  - When building with `CROSS=1 ./swctl build ...`, `autosetup` treats `CROSS=1` as a tool prefix string `"1"` and attempts to invoke `1cc`, `1gcc`, `1ar`, `1ld`.
  - Recipes using `autosetup` must invoke configure with `CROSS="" ./configure ...` to ensure native tools (`cc`, `ar`, etc.) are resolved correctly.
